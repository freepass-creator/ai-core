## 언제 쓰는가

파일·시트·DB에서 얻은 데이터를 공통 읽기 계층으로 제공하고 합계·귀속을 검증할 때 사용합니다.

## 핵심 원칙

원본 존재, 내용 일치, 의미 분류, 계약 귀속, 보류 사유는 별도 축입니다. 해시 일치는 원천 내용의 동일성을 보여줄 뿐 그 돈의 성격이나 계약 귀속을 확정하지 않습니다.

원자·색인·캐시는 소비를 돕는 구조입니다. 프로젝트가 지정한 정본과 버전을 확인하고 새 규칙을 만들기 전 기존 구현을 찾습니다.

## 실제 절차

1. 현재 데이터 지도와 읽기 진입점을 찾아 어떤 원천·기간·버전을 제공하는지 확인합니다. 로컬 지도에 DB 자료가 빠졌는지도 승인 범위 안에서 확인합니다.
2. 색인으로 필요한 값만 읽을 수 있으면 큰 원본 전체를 반복 파싱하지 않습니다. 색인의 원본 버전·내용 해시를 확인하고 낡으면 원본으로 재검증합니다. 크기/mtime만으로 모든 변경을 탐지한다고 보장하지 않습니다.
3. 같은 실행에서 읽고 수정하고 다시 읽는 흐름은 메모리 캐시 무효화를 검사합니다. 저장 함수가 원본·색인·캐시를 일관되게 갱신하는지 봅니다.
4. 합계 전에 대표 행과 기간별 행을 펼쳐 동일 사본 유입·단위·누락을 확인합니다. 파일 ID가 다르더라도 내용이 같은 사본일 수 있고 이름이 같아도 다른 원본일 수 있습니다.
5. 전체 거래열 해시는 명시된 정규화·정렬 기준 아래 비교합니다. 행 중복은 계정·날짜·거래키·금액·잔액·원천을 함께 봅니다. 잔액 일치 하나만으로 삭제하지 않습니다.
6. 중복 후보의 원본과 참조 ID를 보존합니다. 집계 제외가 필요하면 근거·버전·대상 행을 따로 기록하고 승인된 집계 계층에서 적용합니다.
7. 판정 규칙을 중앙화했다면 실제 소비 코드가 그 규칙을 읽는지 확인합니다. 규칙 버전을 올리고 새 결과와 옛 결과를 비교한 뒤 채택하며 과거 결과를 무작정 덮지 않습니다.
8. 원천 확인/의미 후보/귀속 상태/보류 사유를 각각 저장합니다. 보류 사유가 지워진 `null`은 “문제 없음”이 아니라 유실 가능성으로 검사합니다.
9. 원천 기간이 비어 있으면 “자료 미확인”으로 표시합니다. 원천 구멍에 걸린 대상을 입금 없음·미납 확정으로 올리지 않습니다.

DB와 Drive 특성은 [파이어베이스·드라이브](파이어베이스-드라이브.md), 검증 실행은 [고쳤다와 돈다는 다르다](고쳤다와-돈다는-다르다.md)를 봅니다.

10. 원천→정제→판매→ERP의 결과를 같은 기준시점과 분모로 대조합니다. 빈 사전·급격한 삭제량은 원인 확인 전 중단 조건으로 두고, 모르는 날짜·요율·귀속을 임의의 0이나 확정값으로 채우지 않습니다.

## 잘못된 예

- 내용 해시가 맞으니 계약 귀속까지 VERIFIED로 올립니다.
- 잔액이 같다는 이유만으로 원본 거래를 삭제합니다.
- 규칙 파일만 만들고 실제 소비자는 옛 정규식을 계속 사용합니다.
- 없는 기간을 입금 0으로 보고합니다.
