## 언제 쓰는가

승인된 연락처를 Google 계정에 추가·수정하거나 서버 기록과 휴대폰 표시의 차이를 확인할 때 사용합니다.

## 핵심 원칙

현재 표준 경로는 계정·범위가 확인된 OAuth 연결입니다. **Google CardDAV는 OAuth 2.0과 HTTPS를 요구합니다.** 과거 앱 비밀번호/Basic 인증 성공 서술은 현재 지원 절차로 재사용하지 않습니다. [Google CardDAV 공식 문서](https://developers.google.com/people/carddav)

명시한 계정의 연결이 없으면 멈춥니다. 기본 계정으로 조용히 바꾸지 않습니다. 연락처 추가·덮어쓰기·삭제는 실제 대상과 내용을 확인한 직전 승인이 필요합니다.

## 실제 절차

1. 계정과 연락처 범위를 확인하고 현재 연결의 최소 OAuth 권한을 점검합니다. 기존 연락처를 수정한다면 원문과 복구 가능한 사본을 확보합니다.
2. 이름·조직·전화·메모의 필드 매핑을 미리 보여줍니다. vCard의 `FN`·`N`·`ORG`·`NOTE`는 용도가 다르며 기기별 표시 방식이 다를 수 있습니다.

   검수 중 추가된 운영 교훈: 업무폰에서 표시이름에 최초 저장일을 붙이기로 정했다면 그 날짜를 정본에 한 번 저장하고 재동기화 때 그대로 읽습니다. 매번 오늘 날짜로 다시 만들지 않습니다. 이름·회사·저장일 중 무엇을 표시할지는 사용 목적과 실제 기기 화면을 확인해 정하며 모든 연락처의 보편 규칙으로 강제하지 않습니다. 이 추가 내용도 이번 실서비스 재현은 없습니다.
3. 동일인 판정 키와 업데이트 대상을 명시합니다. 내가 정한 href가 같다는 이유만으로 중복·동시 수정 위험이 사라지지 않습니다. 기존 UID·ETag와 조건부 쓰기 지원을 확인합니다.
4. DRY RUN으로 생성·수정·변경 없는 항목·충돌 수를 나누고 승인 후 최소 범위를 실행합니다.
5. 서버 재조회로 실제 필드와 건수를 확인합니다. 요청을 보낸 개수만으로 완료 처리하지 않습니다. 목록 조회 실패는 API의 보편적 미지원으로 단정하지 말고 요청 형식·권한·공식 규격을 검사합니다.
6. 휴대폰에는 대상 계정의 연락처 동기화를 확인합니다. 서버 저장과 폰 표시를 별도 상태로 보고합니다. 전화 화면의 이름/조직 표시도 실제 기기에서 확인합니다.
7. 연결 경로가 없으면 사용자가 CSV/vCard 가져오기를 선택할 수 있습니다. 현재 Google 연락처의 지원 양식으로 샘플을 확인하고 수동 가져오기 역시 중복·필드 손실을 재검사합니다.

과거 전용 스크립트는 인증 방식·계정 fallback·덮어쓰기 조건을 검토하기 전 실행 예제로 제공하지 않습니다. 로그인과 비밀 입력은 현재 환경의 인증 절차를 따릅니다.

## 잘못된 예

- 앱 비밀번호가 있으니 OAuth 없이 된다고 안내합니다.
- 지정 계정이 없어서 다른 기본 계정에 연락처를 넣습니다.
- 같은 URL에 PUT했으니 기존 내용 손실이나 중복은 없다고 보장합니다.
- 서버 저장 성공을 휴대폰 동기화 완료로 보고합니다.

## 체크리스트

- [ ] OAuth/HTTPS 및 실제 대상 계정이 확인됐는가
- [ ] 변경 전후 필드와 충돌·중복을 확인했는가
- [ ] 현재 원문/ETag와 승인 대상이 일치하는가
- [ ] 서버 재조회와 폰 동기화를 나눠 확인했는가
- [ ] 개인정보 보관·전달 범위가 승인됐는가
