## 언제 쓰는가

Next.js의 요청 진입점·호스트 rewrite·인증 경로를 변경하거나 버전 업그레이드를 검토할 때 사용합니다.

## 핵심 원칙

먼저 설치된 Next.js 버전과 현행 진입점을 확인합니다. deprecated와 removed를 구분합니다. Next 16의 Proxy는 Node.js 런타임을 사용하며 Edge 런타임 요구가 있다면 공식 안내에 따라 Middleware 유지 여부를 검토합니다. [Next.js 16 업그레이드](https://nextjs.org/docs/app/guides/upgrading/version-16)

파일명 변경은 인증 경로를 바꾸는 작업일 수 있습니다. 기존 matcher·헤더·쿠키·허용/차단 동작을 누락하지 않습니다.

## 실제 절차

1. 현재 `middleware`/`proxy` 파일과 위치, 런타임 요구, matcher, 인증 책임을 읽습니다. 같은 역할의 파일을 새로 덧붙이지 말고 설치 버전의 동시 존재 규칙을 확인합니다.
2. 전환이 적합하면 기존 동작을 보존하는 diff를 준비합니다. Edge 요구가 있다면 이름만 바꾸지 않습니다. API 인증은 필요한 서버 처리 경계에서도 확인합니다.
3. dev 서버의 변경 반영 여부를 실제 응답으로 검사합니다. 재시작이 필요했던 과거 사례는 보존하되 모든 버전에서 HMR이 불가능하다고 단정하지 않습니다.
4. 주소를 바꿀 필요가 있는지에 따라 redirect/rewrite를 선택합니다. rewrite 후 내부 대상·쿼리·인증·캐시·직접 접근 URL이 어떻게 처리되는지 검사합니다. 재진입 여부도 현행 구성에서 확인합니다.
5. 화면의 정체성을 URL 문자열 하나로 판정하지 말고 안정된 앱 식별자를 사용합니다. 동일 화면의 원래 URL·rewrite URL을 각각 시험합니다.
6. 로컬 Host 헤더 시험은 라우팅 로직 확인의 보조 수단입니다. 실제 배포의 host 신뢰 경계·TLS·도메인·접근 보호 검증을 대신하지 않습니다.
7. 한글 등 비ASCII URL은 지원되는 URL 생성·퍼센트 인코딩 방식을 사용합니다. 오류가 발생한 단계가 빌드/실행/리다이렉트 응답 중 어디인지 로그로 구분합니다.
8. dev/build의 출력 경로와 동시 실행 충돌은 버전별로 확인하고 분리합니다. 타입검사만 수행한 상태를 빌드 검증 완료로 보고하지 않습니다.
9. 원격 commit/deployment ID·alias를 확인하고 실제 라우트·인증·정적 파일을 조회합니다. 새 문구를 청크에서 찾는 검사는 보조 증거이며 최신 배포 전체의 정상 동작을 증명하지 않습니다.

## 잘못된 예

- 기존 인증 Middleware를 읽지 않고 Proxy를 새로 만듭니다.
- Edge 요구를 확인하지 않고 파일명만 바꿉니다.
- 로컬 라우트가 있으니 배포본에도 있다고 보고합니다.
- 타입검사만 통과한 상태를 운영 배포 검증 완료로 표현합니다.

## 체크리스트

- [ ] 설치 버전·공식 업그레이드·런타임 요구를 확인했는가
- [ ] 기존 matcher/인증/쿠키 동작을 보존했는가
- [ ] 직접 URL과 rewrite URL을 모두 검사했는가
- [ ] dev/typecheck/build/실배포 검증을 구분했는가
- [ ] 원격 라우트와 권한 흐름을 실제 확인했는가
