## STD-001 새 노하우를 등록하거나 고칠 때

상태: 제안 규격 · 적용: 이 KB · 검토일: 2026-09-08 · 운영 적용: 미실시.

### 언제 쓰는가

새 사례를 추가하거나 중복·오류·오래된 처방을 고칠 때.

### 핵심 원칙

정본은 저장소의 `docs/aiknowhow` 하나다. 이 통합판은 사용자 승인으로 반영한 문서이며 실서비스 검증 상태는 항목별로 구분한다. README는 길 안내만 하고 실행 절차를 복제하지 않는다. 프로젝트의 AGENTS·운영 규칙이 원본이며 이 KB가 승인이나 권한을 새로 만들지 않는다.

### 실제 절차

1. 기존 제목·ID·키워드부터 검색한다. 같은 목적·조건이면 기존 카드를 고치고, 다른 환경이면 적용 범위를 명시한 카드로 추가한다.
2. 기존 `KH-001…036`, 운영 사례 `OP-001…019` ID를 유지한다. 통합 시 사라진 ID에는 대체 ID를 기록하고 다른 뜻으로 재사용하지 않는다.
3. 각 카드는 **언제 쓰는가 / 핵심 원칙 / 실제 절차 / 잘못된 예 / 체크리스트** 다섯 절을 가진다. 실제 절차 안에 전제조건·중단 조건·복구 방법을 적는다.
4. 메타데이터는 출처, 적용 환경/비적용 범위, 상태, 원문 확인일, 실제 실행 검증일과 증거 위치를 기록한다. 미실시는 날짜 대신 `미실시`로 남긴다. 원문 읽기·공식 문서 확인·로컬 재현·실서비스 검증을 구분한다.
5. 상태는 `권장 절차 / 과거 관찰 / 로컬 재현 / 실서비스 검증 / 재검증 필요 / 사용 중지` 중 고른다. 특정 예제의 로컬 재현을 문서 전체의 실서비스 검증으로 승격하지 않는다.

   `초안·제안·검수안`은 편집 단계이며 증거 상태와 별개다. 기존 “기록 회수 및 정정 초안; 실서비스 미재현” 문구는 편집 단계와 미검증 범위를 설명한다. 이번 절차는 권장 절차이며, 인용된 과거 성공은 과거 관찰로 취급한다. 한 문서에 여러 증거 수준이 있으면 해당 항목 바로 옆에서 구분한다.
6. 가격·쿼터·로그인·연결·도구 인자는 사용할 때 재확인한다. 제품 주요 버전, 계정/권한, 프로젝트/대상, 정책이 바뀌거나 실패가 재발하면 기존 실행 검증을 재검증 필요로 내린다. 모든 지식에 임의의 동일 만료일을 붙이지 않는다.
7. 쓰기·발송·배포처럼 외부 영향이 있는 절차는 현재 사용자 지침의 대상·범위·직전 승인 조건을 따른다. 미확인 실행 레시피는 보류하며 읽기 전용 진단과 분리한다.
8. 이견은 원본·공식 근거 → 재현 테스트 → 로그 → AI 추론 순으로 판정한다. 최신 날짜만으로 관련 없는 환경의 테스트를 우선하지 않는다.
9. 전체 문서의 ID·링크·코드 블록·필수 절과 변경 목록을 검사한다. 개인정보 패턴 검사는 후보 탐지일 뿐 공유 적합성 보증이 아니다.

   실제 절차와 체크리스트에는 검사가 증명하는 범위·증명하지 못하는 범위·판정을 뒤집는 조건을 적는다. 예: “링크 경로 존재 확인”은 원격 로그인 접근이나 내용 정확성을 증명하지 않는다. 접근 불가·부분 결과·반례가 발견되면 해당 완료 판정을 보류한다. 필드를 늘리기보다 기존 다섯 절 안에서 설명한다.
10. 반영 전 원격/로컬 기준 버전과 변경 유입을 재조회한다. Git 이력과 이관대조표에 제외·대체 이유를 남긴다. 실제 병합·동기화 후 바이트 대조와 외부 참조 링크까지 확인한다.

중단 조건: 대상/승인/원본 버전 불명, 민감정보 포함, 기존 사용자 변경과 충돌, 검증 미통과. 해당 범위만 보류하고 진단 가능한 일은 계속한다. 복구는 해당 변경의 이전 버전으로 되돌리는 계획을 먼저 마련하며 다른 사람의 변경을 덮지 않는다.

### 잘못된 예

오늘 문서를 읽었다는 이유로 모든 카드의 실행 검증일을 오늘로 쓰거나, 새 정정표만 붙이고 원문의 틀린 명령은 계속 복사 가능하게 둔다.

### 체크리스트

- [ ] 대표 카드와 적용 범위가 명확한가
- [ ] 다섯 절과 출처·상태·실행 검증 구분이 있는가
- [ ] 이전 항목의 고유 교훈과 제외 이유를 추적할 수 있는가
- [ ] 현재 규칙을 대체하거나 실행 권한을 확대하지 않는가
- [ ] 최종 문서 전체를 검사하고 재조회했는가

## STD-002 다음 단계로 발전시킬 기능

상태: 제안 · 적용: 지식베이스 운영 · 실제 운영 검증: 미실시.

### 언제 쓰는가

같은 설명·실수·연결 확인을 반복하고 있을 때.

### 핵심 원칙

자동화는 유지 비용과 실제 반복 횟수에 비례해 도입한다. 모든 기능을 한 번에 설치하지 않는다.

### 실제 절차

1. **작업별 입구:** README에서 “자료 만들기/이어하기/배포하기/오류 찾기”로 필요한 카드만 연다.
2. **기능 확인표:** 자주 쓰는 연결만 도구명·버전·읽기/쓰기 범위·마지막 실제 확인일·현재 제약·다음 확인 조건으로 관리한다. 자격증명 값은 적지 않는다.
3. **실패 접수:** `관련 카드 ID / 기대 결과 / 실제 결과 / 환경 / 재현 자료 위치 / 영향 / 임시 조치 / 원인 / 재발 검사`를 기록하고 기존 중복 사고에 연결한다.
4. **반복 절차의 skill 전환:** 안정된 절차와 검증법이 생긴 뒤 해당 주제 카드를 참조하는 얇은 skill을 제안한다. 본문을 복제하지 않는다. [공식 skill 구조](https://learn.chatgpt.com/docs/build-skills)는 지침·선택적 스크립트·참고 자료를 묶을 수 있다. 이번 작업에서는 설치하거나 전역 지침을 바꾸지 않았다.
5. 먼저 로컬 문서 검사만 자동화한다. 예약·외부 발송·자동 쓰기는 별도 목적과 실행 범위가 정해진 뒤 구성한다.

### 잘못된 예

아직 불안정한 과거 명령을 반복 실행하게 만들거나, 모든 도구 상태를 거대한 표로 만들어 갱신하지 않는다.

### 체크리스트

- [ ] 사용 빈도에 비해 관리 비용이 합리적인가
- [ ] 설명 원본을 복제하지 않고 참조하는가
- [ ] 자동 실행 범위가 명시되어 있는가
