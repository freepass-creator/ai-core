## 언제 쓰는가

기존 프로젝트의 도메인 연결을 바꾸거나 공동 작업 중 격리된 변경을 준비할 때 사용합니다.

## 핵심 원칙

도메인 연결과 앱의 호스트 라우팅·인증은 한 흐름입니다. 도메인을 옮긴 뒤에야 호스트 설정을 고치는 순서를 기본 절차로 삼지 않습니다. 운영 전환은 대상·영향·복구안을 준비하고 직전 승인을 받습니다.

프로젝트 규격·현행 코드·배포 설정이 정본입니다. 과거 계정·DNS 값·포트·전환 시간을 현재 보장으로 사용하지 않습니다.

## 실제 절차

1. 현재 팀/프로젝트/도메인/alias/배포/보호를 읽기 전용으로 확인합니다. DNS 제공자와 레코드, 앱의 호스트 허용표·rewrite·인증 진입점을 함께 조사합니다.
2. 받을 프로젝트가 새 호스트를 올바른 화면으로 처리하는지 미리 검증합니다. 기존 서비스 영향과 되돌릴 대상/설정을 준비합니다. 도메인 강제 이전 옵션은 영향 확인 없이 실행하지 않습니다.
3. 승인 후 전환하고 실제 도메인에서 고객 화면·정적 자산·익명/인증 접근·연결 데이터를 확인합니다. HTML의 특정 문자열은 보조 증거이며 commit/deployment/alias 검증을 대체하지 않습니다.
4. squash merge 뒤 후속 작업은 최신 main 기준 새 브랜치로 시작하는 방식을 우선 검토합니다. 기존 branch 재사용·rebase·cherry-pick은 커밋 그래프와 실제 diff를 확인하고 필요한 미반영 커밋만 가져옵니다.
5. 다른 세션의 dirty 작업 트리를 보호하려면 별도 worktree를 사용합니다. 공유 `node_modules` 정션은 버전 불일치·동시 설치 변경 위험이 있어 독립 설치를 우선하고, 공유한다면 lockfile 일치와 변경 금지를 확인합니다.
6. 환경 파일에는 비밀값이 있으므로 필요 범위와 보관 위치를 확인합니다. 전체 `.env` 복사를 기본으로 하지 않으며 별도 환경에 최소 권한 값을 제공합니다.
7. 미리보기 실행 설정이 어느 checkout에서 읽히는지 현재 도구로 확인합니다. 다른 세션의 설정을 임의 수정하지 않고 포트 충돌과 서버 준비를 검사합니다. 첫 navigation이 로그인으로 돌아오면 인증/리다이렉트 상태를 관찰한 뒤 판단합니다.
8. 브랜드 SVG는 공식 자산과 비율을 유지합니다. 배경과 fill/currentColor를 확인하고 viewBox를 임의로 좁혀 자산 일부를 자르지 않습니다. 좌표·사용권·브랜드 지침을 확인하며 칸 크기를 콘텐츠에 맞춥니다.
9. 타입검사·프로젝트 디자인/라우트/토큰/UI/브랜드 검사를 현행 명령으로 실행합니다. 인증 자료가 없어 skip된 검사는 통과가 아닙니다. lint/build 명령은 설치된 프레임워크 버전에서 확인합니다.
10. 화이트라벨 설정은 현행 프로젝트 표·정본 CI 데이터에서 읽습니다. 한 행 추가만으로 완성된다고 단정하지 않고 라우트·호스트·콘텐츠·접근 흐름을 검증합니다.

11. 비공개 파일은 업로드 전에 보호가 적용되는지 확인합니다. 플랜별 범위·실제 target·aliases·기존 인증을 조회하고 민감 파일 없는 샘플로 익명 차단을 먼저 시험합니다. 배포 파일은 허용 목록·내용 해시·메타데이터로 점검하며 HTML뿐 아니라 JS·이미지·직접 자산 URL도 확인합니다.
12. 노출 의심 사고는 배포 ID·시간·대상·허용 목록을 보존하고 승인된 사고 대응 범위에서 차단합니다. 제거/기존 URL·production·preview·정적 자산을 다시 확인합니다. 우회 토큰의 값은 남기지 않고 존재·폐기 결과만 기록합니다.
13. 사고 당시와 차단 후를 분리해 보고합니다. 현재 404/로그인 차단은 과거 노출 부재의 증거가 아니며, 열람 로그가 없으면 실제 열람 여부는 미확인입니다. 검증 편의를 위한 우회 토큰 생성은 자동으로 하지 않습니다.

## 잘못된 예

- 도메인만 옮겨 고객이 업무용 로그인 화면을 보게 합니다.
- 공유 의존성 폴더에 설치를 실행해 다른 세션의 환경을 바꿉니다.
- 원격에서 문자열 하나가 보이니 전체 배포가 정상이라고 보고합니다.
- 인증이 없어 건너뛴 검사를 PASS로 적습니다.
