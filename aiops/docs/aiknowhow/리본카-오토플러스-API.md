## 언제 쓰는가

사용 권한이 있는 외부 재고 사이트에서 화면 데이터와 API 응답이 다른 이유를 조사할 때 사용합니다.

## 핵심 원칙

화면에서 못 읽었다는 것은 데이터가 없다는 뜻이 아닙니다. 공식/승인된 API를 우선하며, 사이트의 인증·접근 제한을 임의로 해제하지 않습니다. 과거 사이트의 특정 헤더·토큰·경로 관찰을 현재 필수 규격으로 단정하지 않습니다.

## 실제 절차

1. 승인된 대상 페이지와 요청 한 건을 관찰합니다. HTTP 상태·응답 오류코드·요청 형식·세션 일치를 분리합니다.
2. 과거 사례에서는 AJAX 구분 헤더, form-urlencoded 본문, 해당 페이지의 토큰/쿠키/CSRF, 일치하는 Referer가 응답에 영향을 주었습니다. 현재도 같은지는 공식 규격 또는 허용된 실제 요청을 통해 확인합니다. JSON과 form 요청을 혼동하지 않습니다.
3. 토큰·쿠키는 로그나 KB에 기록하지 않습니다. 만료 응답이 와도 응답 텍스트의 새 값을 무조건 신뢰해 재시도하지 말고 문서화된 갱신 절차와 재시도 한도를 적용합니다.
4. 추천 목록과 전체 재고를 구분합니다. 페이지네이션·필터·sitemap 후보를 교차확인하되 sitemap만으로 전수라고 보장하지 않습니다.
5. 요청 성공·실패·확인 대상 분모를 나눕니다. 일부 실패가 있으면 전체 수집 완료로 보고하지 않습니다.
6. 차량 속성과 가격표, 약관/정책의 출처를 나눕니다. API에 없는 정책을 화면 공통 문구로 보충할 때 적용 상품·시점·조건을 확인하고 미확인이면 보류합니다.
7. 구현 정본은 해당 프로젝트의 현행 수집 코드입니다. 이 문서는 과거 문제해결 구조를 설명하며 배치 수집·운영 반영 권한을 만들지 않습니다.

## 잘못된 예

- 404면 항상 헤더 문제라고 단정합니다.
- 추천 목록 개수를 전체 재고로 보고합니다.
- 페이지 토큰이나 실제 차량 식별자를 공용 예제로 저장합니다.
- 공통 약관을 모든 상품의 확정 정책으로 복사합니다.
