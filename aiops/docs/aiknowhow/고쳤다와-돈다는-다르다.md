## 언제 쓰는가

자동 파이프라인·감사 도구·상태 기록을 수정한 뒤 “반영됨”과 “실행됨”을 구분할 때 사용합니다.

## 핵심 원칙

코드 존재, 실행 경로 도달, 기록 저장, 외부 반영, 사용자 결과는 각각 증거가 필요합니다. 0건은 실제 대상 없음일 수도 있고 검사 경로가 실행되지 않은 결과일 수도 있습니다.

검사 규격은 운영 정본에서 가져오되, 기대 결과 검사는 구현을 그대로 복제하지 않습니다. 공통 enum을 import하는 것과 같은 잘못된 알고리즘을 검사에도 복사하는 것은 다릅니다.

## 실제 절차

1. 플래그별 진입점과 조기 반환·`process.exit()` 위치를 확인합니다. 여러 모드를 함께 주는 조합에서 필요한 단계가 모두 도달 가능한지 검사합니다. 종료는 제어 흐름에 맞게 설계하며 무조건 파일 끝 하나로 제한하지 않습니다.
2. 실제 후보가 있는 작은 DRY RUN 입력으로 시작·종료·처리 분모를 봅니다. 0건이면 원천의 후보 수와 비교합니다.
3. 상태 파일을 읽는 코드뿐 아니라 쓰는 호출·경로·오류 처리도 확인합니다. 한 회차 뒤 파일 존재·변경 시각·실제 내용이 바뀌었는지 재조회합니다.
4. 매뉴얼의 경고 조건과 실제 코드의 분류 목록을 대조합니다. 기간·상태·키 규격이 바뀌었다면 소비 함수와 검사 도구까지 확인합니다.
5. 외부 발행은 응답 성공만 보지 말고 발행된 범위를 같은 기준시점으로 재읽습니다.
6. 발행을 막아야 할 위험과 단순 정비 알림을 구분합니다. 필수 원천·권한·금액 등 핵심 값 누락은 빈칸이라도 중단 사유일 수 있습니다.
7. 재발 사례를 회귀 조건으로 남기고, 각 검사의 미실행·부분 성공·실패를 통과와 분리합니다.

AI 검토 절차는 [AI-교차검증](AI-교차검증.md), 반복 파이프라인 사례는 [가격 파이프라인](price-pipeline.md)을 함께 봅니다.

8. 요구사항마다 증거를 대응합니다. 코드의 타입/테스트/빌드/핵심 흐름, 문서의 수치/참조/렌더, UI의 기기/빈값/오류/권한 상태, 배포의 실제 URL/연결 데이터/접근 보호를 작업 성격에 맞게 확인합니다. 생성 도구는 설치나 연산 테스트 외 실제 결과물 한 건이 필요합니다.
9. 판정은 원본·공식 근거 → 재현 가능한 검사/계산 → 실행 로그 → AI 추론 순으로 합니다. 범위와 시점을 명시하고 완료 직전에 오류·누락·미검증을 다시 점검합니다. 독립 검토의 실행 기준은 [AI 교차검증](AI-교차검증.md)의 대표 절차를 따릅니다.

## 잘못된 예

- 조기 종료 아래의 로그만 분석해 “해당 상태 0건”이라고 보고합니다.
- 상태 파일을 읽기만 하는데 “중복 처리가 방지된다”고 주장합니다.
- 검사에 규격 목록을 손으로 복사하고 최신 정상값을 오류로 보고합니다.
- 빈칸은 언제나 경고라고 하여 필수 자료 누락을 발행합니다.

## 체크리스트

- [ ] 플래그 조합별 실행 도달 증거가 있는가
- [ ] 기록 파일이 실제 생성·변경됐는가
- [ ] 분모와 0건의 원인을 확인했는가
- [ ] 검사 규격과 독립적인 기대 결과가 있는가
- [ ] 외부 반영 후 재조회했는가
