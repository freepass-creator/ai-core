## 언제 쓰는가

로컬 자료와 DB·Drive 원천을 대조하거나 승인된 데이터 갱신을 설계할 때 사용합니다.

## 핵심 원칙

정본 위치는 프로젝트 규칙에 따릅니다. 로컬 원자만 조사하고 연결 DB에 자료가 없다고 결론 내리지 않습니다. 반대로 DB의 검증 상태도 근거를 확인하지 않고 그대로 믿지 않습니다.

Firestore와 Drive의 실제 쓰기·삭제·대량 조회는 지정 범위와 현재 통제를 따릅니다. 기존 잠금 래퍼가 승인이나 검증을 대체하지 않습니다.

## 실제 절차

1. 지정 범위의 컬렉션/파일 목록과 건수를 먼저 조회합니다. 필요한 필드·필터·페이지에 한정해 읽고 전체 다운로드는 필요성과 범위를 확인합니다.
2. 원천 해시 검증과 의미·귀속 검증을 분리합니다. 플랫폼 결과와 다른 계산 결과를 무조건 합치지 말고 같은 버전으로 나란히 대조합니다. [원자 다루기](원자-다루기.md)
3. Drive의 파일 ID는 리소스 식별자입니다. 다른 ID의 동일 사본은 내용으로 비교하고 같은 이름의 다른 원본은 보존합니다. Google-native 문서에는 업로드 바이너리와 같은 checksum 제공을 기대하지 않으며 필요한 의미 데이터의 정규화 해시를 정의합니다.
4. 파일명에서 추출한 차량 등 식별자는 후보입니다. 문자열 패턴만으로 정본 식별자를 확정하지 않습니다.
5. 저장 제한은 현재 [Firestore 공식 할당량](https://firebase.google.com/docs/firestore/quotas)을 확인합니다. 과거 “문서당 필드 20,000개”와 “항상 초당 1회” 설명은 일반 규칙으로 사용하지 않습니다. 크기·중첩·인덱스·쓰기 경합을 구분합니다.
6. 사람이 관리하는 매뉴얼과 코드 규격은 기존 Git/프로젝트 규칙으로 관리하고, DB 복사본이 필요하면 단방향 생성·버전 연결을 설계합니다. DB에 저장할 수 있다는 사실만으로 별도 정본을 만들지 않습니다. 시트도 업무별로 정본/출력/사용자 입력 역할을 구분합니다.
7. `set(..., merge:true)`는 누락 키를 자동 삭제하지 않습니다. 중첩 맵 전체 교체, 명시 필드 삭제, 기존 키 보존을 구분하고 현재 SDK의 field path·delete sentinel·빈 맵 동작을 작은 샘플로 검증합니다.
8. 원천이 맵을 제공하지 않은 경우와 제공한 빈 맵은 다릅니다. 문서 생성 후 맵 교체처럼 두 쓰기를 결합할 때 원자성·문서 미존재·충돌을 테스트한 뒤 승인 범위에만 적용합니다.
9. 빈 문자열/null이 “모름”인지 “명시 삭제”인지 필드별 규격으로 정합니다. 일괄 제거 함수는 중첩 데이터와 의도한 삭제를 놓칠 수 있습니다. 삭제 허용은 필드 이름만이 아니라 상태·연료 등 실제 업무 조건으로 제한합니다.
10. DRY RUN 전후 차이·삭제량·보존 필드·버전을 기록하고 승인된 실행 후 동일 범위를 재조회합니다.

## 잘못된 예

- 해시가 검증됐다는 DB 상태로 대여료 귀속까지 확정합니다.
- merge가 원천에서 사라진 중첩 키를 자동 제거한다고 믿습니다.
- 원천에 없는 빈값으로 이미 확인한 분류를 덮습니다.
- 문서 제한·처리량을 오래된 고정 숫자로 설계합니다.

## 체크리스트

- [ ] 정본·조회 범위·기간이 맞는가
- [ ] 파일 ID와 내용 동일성을 구분했는가
- [ ] SDK와 공식 제한을 확인했는가
- [ ] 미제공/빈값/명시삭제를 구분했는가
- [ ] 맵 교체·문서 미존재·동시 수정 테스트가 있는가
- [ ] 실행 후 보존 필드와 변경 범위를 재조회했는가
