## KH-019 먼저 수동 한 회차, 그다음 예약

출처: U1, L1, M2.
상태: 과거 기록을 바탕으로 정리한 권장 절차(이번 실행 재현 없음).
현재 열람: 2026-09-08의 KB 스냅샷 전체 읽기. 이전 세션 원문 재검수는 아님.
마지막 실행 검증: 미실시. 원문 재열람은 당시 실행 결과의 재현 검증을 뜻하지 않는다.

### 언제 쓰는가

시간별 동기화·모니터·반복 파일 처리를 만들 때.

### 핵심 원칙

트리거·대상·읽기/쓰기·알림·실행 위치를 명시한다. 기존 자동화의 범위를 조용히 넓히지 않는다.

### 실제 절차

1. 기존 자동화 이름/목적을 조회해 중복 여부를 확인한다.
2. 읽기 전용 또는 DRY RUN으로 한 회차를 끝까지 검증한다.
3. 시간대·주기·중복 키·재시도 한도·종료 조건을 정한다.
4. 상태가 변하지 않으면 조용히, 중요한 변화·실패·사람 조치 때만 알린다.
5. 요청된 예약 기능으로 등록하고 저장된 설정을 확인한다.
6. 로컬 실행은 절전·로그아웃·네트워크 영향을 확인한다. 기존 aiops의 Apps Script 트리거 금지 규칙을 보존한다.

### 잘못된 예

“매시간”이라 적은 문서를 실제 예약 등록으로 착각하거나, PC가 잠든 동안에도 로컬 작업이 돈다고 가정한다.

### 체크리스트

- [ ] 실제 예약이 저장됐는가
- [ ] 시간대·실행 위치가 명시됐는가
- [ ] 알림이 의미 있는 변화에 한정되는가
- [ ] ★래퍼 `.cmd` 가 `exit /b %RC%` 로 끝나는가
- [ ] ★래퍼에 `jikimi-allim` 줄이 있는가 (알림이 «본체 밖»에 있는가)
- [ ] ★켜는 작업의 `lib/jikimi.mjs` 작업표 `지켜본다` 를 `true` 로 바꿨는가
- [ ] ★`aiops-jikimi`(묵음 점검)가 걸려 있는가 — 없으면 「안 돌았다」를 아무도 못 본다

### ★작업이 죽었을 때 어떻게 알게 되나 (2026-09-16)

그전엔 **닿는 경로가 하나도 없었다.** 로그뿐이고 아무도 안 읽는다. `aiops-light` 가 그날 10:10 회차에
`0xC000013A`(강제종료)로 끊겼는데 아무 알림이 없었다. freepasserp4 는 같은 까닭으로 **매시 동기가
사흘 멈춰 있었는데 아무도 몰랐다** — 알림 코드가 작업 «안»에 있어서 **작업이 죽을 때 알림도 같이 죽었다.**

**★그래서 알림은 본체 밖, 래퍼(`.cmd`)에 둔다.** `.cmd` 는 node 가 죽어도 다음 줄을 계속 돈다.

```
node <본체> ...
set RC=%ERRORLEVEL%
echo ---- exit %RC% ---- >> logs\...log      ← cmd.exe 만으로 쓴다. node 가 못 떠도 남는다
node scripts\jikimi-allim.mjs --jageop=<작업이름> --code=%RC% --bonaenda >> logs\jikimi.log 2>&1
exit /b %RC%                                 ← ★작업의 종료코드를 넘긴다(지킴이 것이 아니라)
```

지킴이는 **무슨 일이 있어도 `exit 0`** 이다. 지킴이가 넘어져서 작업의 종료코드를 덮어쓰면 안 된다.

| 무엇 | 어디 |
|---|---|
| 판단·글짓기(순수 함수) · **작업표** | `lib/jikimi.mjs` |
| 한 회차가 끝난 뒤 알림 (래퍼가 부른다) | `scripts/jikimi-allim.mjs` |
| 「안 돌았다」 점검 | `scripts/jikimi-jeomgeom.mjs` · 래퍼 `scripts/jikimi.cmd` |
| 마지막 성공 시각(맥박) | `logs/jikimi-maekbak.json` (gitignore — 그 PC 의 실행 사실이지 정본이 아니다) |

**★「안 돌았다」는 종료코드로 못 잡는다.** 작업이 아예 안 뜨면(꺼짐·PC 꺼짐·조건에 걸려 건너뜀)
종료코드 자체가 없다. 그래서 맥박에 마지막 성공 시각을 남기고, **작업과 다른 프로세스**인
`aiops-jikimi` 가 그걸 읽는다 — 작업이 한 번도 안 떴어도 지킴이는 뜬다. 한계는 「기대 주기 + 한 회차」다
(daily 30시간 · light 9시간 · 과태료 30시간). 맥박을 시트·Firestore 에 두지 않은 까닭:
**네트워크가 막히거나 할당량이 마르면 바로 그때 못 쓰는 저장소**이기 때문이다. 기록이 아예 없으면
「안 돌았다」가 아니라 **「모른다」**로 적는다 — 한 번도 안 돈 것과 기록을 잃은 것을 구별할 수 없다.

**★시끄러우면 꺼진다.** 두 조건 중 하나일 때만 보낸다 — ① 상태가 **바뀔** 때(성공→실패, 실패→성공(복구),
성공→묵음) ② 같은 실패가 이어져도 **하루 한 번**(한국 날짜). 계속 성공이면 **아무것도 안 보낸다.**

**★켤 때** — 작업을 켜기 전에 `lib/jikimi.mjs` 작업표의 그 줄을 `지켜본다: true` 로 바꾼다.
지금은 전부 `false` 다(대표: 「자동으로 켜는 건 다 꺼」). 켜지도 않은 작업을 매일 「묵었다」고
알리면 그게 바로 사람이 알림을 끄는 길이다. `aiops-jikimi` 는 **등록하지 않았다** — 권하는 시각은
`scripts/jikimi.cmd` 주석에 적어 뒀다(09:30, 직원 출근 뒤라 같은 아침에 읽힌다).

보내는 «방법»은 [메일보내기](메일보내기.md) 그대로다(`C:/dev/mailtool/send_mail.py`).
`scripts/메일보고.mjs` 는 **고치지 않았다** — 그건 「정합성·루틴 보고서」고 이건 「작업이 죽었다」 알림이다.
한 파일에 두 용도를 섞으면 둘 다 망가진다. 기본은 **안 보내는 모드**이고 `--bonaenda` 를 붙여야 보낸다.

일부러 깨뜨려 본 것(발송 없이): ① 종료코드 4 → 알림 글이 만들어진다 ② 종료코드 0 연속 → 안 만들어진다
③ 마지막 성공을 53시간 전으로 놓으니 「묵었다」가 잡힌다. 그 시험에서 **맥박의 마지막 성공을 사람이 읽는
`… (KST)` 꼴로 적어 `Date.parse` 가 NaN 이 되는 버그**를 잡았다 — 기계가 다시 읽는 값은 ISO 로 적는다.

### ★실사례 — 거짓 성공 (2026-09-16)

`.cmd` 는 **마지막 명령의 종료코드**로 끝난다. 과태료 래퍼 둘의 마지막 줄이 로그에 결과를 찍는
`echo` 였고 echo 는 언제나 성공한다. 그래서 node 가 `exit 4` 로 죽어도 작업 스케줄러는
**0(성공)** 을 기록했고, **한 번도 성공한 적 없는 작업이 몇 달째 초록불**이었다.

```
set RC=%ERRORLEVEL%
echo ---- exit %RC% ---- >> logs\...log
exit /b %RC%          ★이 줄이 없으면 실패가 실패로 보고되지 않는다
```

커밋 `ea5132f`. ★**시간대를 「한가한 시각」으로 고르는 것과 「할당량이 남은 시각」으로 고르는 것은 다르다** —
과태료 06:07 은 앞의 기준으로 골랐고, 파이어스토어 무료 할당량은 한국 16시에 리셋돼 06:07 엔 말라 있었다.
★Windows 에서 `.cmd`·`.bat` 을 `spawn` 할 때는 `shell: true` 가 반드시 있어야 한다(없으면 `EINVAL`).
자세한 것은 `docs/과태료-작업지도.md` 「★★예약 작업 — 왜 멈췄나 · 켜기 전에 무엇을 보나」.

## KH-020 재시도·잠금·부분 실패

출처: L1, M2.
상태: 과거 기록을 바탕으로 정리한 권장 절차(이번 실행 재현 없음).
현재 열람: 2026-09-08의 KB 스냅샷 전체 읽기. 이전 세션 원문 재검수는 아님.
마지막 실행 검증: 미실시. 원문 재열람은 당시 실행 결과의 재현 검증을 뜻하지 않는다.

### 언제 쓰는가

동기화와 수동 작업이 겹치거나 일부 단계가 실패할 때.

### 핵심 원칙

재시도가 중복 쓰기를 만들지 않아야 한다. 잠금은 승인과 다르다.

### 실제 절차

1. 실행 ID와 단계별 입력 버전·결과를 기록한다.
2. 같은 항목의 중복 처리 방지 키를 사용한다.
3. 잠금 소유자·만료·적용 범위를 검사하고 무조건 삭제하지 않는다.
4. 재시도 전 앞선 작업이 적용됐는지 재조회한다.
5. 일부 실패라면 성공 범위와 실패 범위를 따로 보고한다.
6. 다음 회차가 복구했는지 실제 결과를 확인한다.

### 잘못된 예

전체 카운트만 성공으로 남겨 중간 단계의 오래된 값과 최신 값을 섞는다.

### 체크리스트

- [ ] 동시 실행이 통제되는가
- [ ] 중복 쓰기를 방지하는가
- [ ] 실패 단계가 로그에서 식별되는가

## KH-020 「한가한 시각」과 「할당량이 남은 시각」은 다른 자원이다 — light 도 같은 벽에 맞았다 (2026-09-17)

대표: 「라이트 시각도 재서 올려」.

`aiops-light` 는 켜져 있었는데 **파수꾼 깃발이 false** 라 아무도 안 보고 있었다. 로그를 열어 보니
**아침 두 판이 매일 죽고 있었다.**

| light 판 | 리셋 뒤 남은몫(대리값) | 실제 결과 |
|---|---|---|
| 10:10 | 36% | **429 · exit 1** |
| 13:10 | 16% | **429 · exit 1** |
| 16:10 | 100% (리셋 직후) | **exit 0 「다 돌았다」** |
| 18:40 | 85% | **exit 0** |

★**경계는 리셋이다.** 파이어스토어 무료 할당량은 태평양 자정(한국시간 16시)에 리셋되고,
그 뒤로 **단조로 줄어든다** — 11시 27% → 13시 16% → **14시 5% · 15시 3%**.
11~15시는 구조적으로 «바닥» 인 구간이라, 거기 잡힌 판은 언젠가가 아니라 **매일** 죽는다.

**★잘 도는 둘은 안 건드리고, 죽는 둘만 옮겼다.**

```
10:10  ->  02:40      13:10  ->  22:40      (16:10 · 18:40 은 그대로)
```

- `02:40` — 잠금 31건(새벽 고요), 남은몫 44%. **아침 출근 때 6시간 반 된 자료**를 보게 한다
- `22:40` — `daily`(20:00)·과태료 본판(21:07) 이 «끝난 뒤». 그 판들의 결과까지 담긴다
- `16:10` — 리셋 직후. **이미 exit 0 으로 증명된 자리**라 손대지 않았다
- `18:40` — 85%, 역시 증명된 자리

★**치르는 값을 밝힌다: 09시~16시 사이에 새로고침이 없다.**
다만 **지금 그 구간은 «실패만» 생산하고 있었으므로 잃는 것이 없다.** 죽는 판은 신선함을 0 으로 준다.

★**모르는 것 — 「남은몫 %」는 잠금 자국을 센 «대리 값»이다.**
잠금을 안 쥐고 읽는 세션도 할당량을 먹으므로 진짜 잔량은 **모른다.**
10:10 은 36% 로 보였는데 죽었다. 그러니 `02:40` 의 44% 도 **안전이 증명된 값이 아니다.**
★다만 이제는 **죽으면 파수꾼이 알린다**(`지켜본다: true`). 실패가 보이면 16~23시 안으로 옮긴다.

**바꾼 명령 (실행함)**

```powershell
$new = @(
  (New-ScheduledTaskTrigger -Daily -At '02:40'), (New-ScheduledTaskTrigger -Daily -At '16:10'),
  (New-ScheduledTaskTrigger -Daily -At '18:40'), (New-ScheduledTaskTrigger -Daily -At '22:40'))
Set-ScheduledTask -TaskName 'aiops-light' -Trigger $new
```

★**다시 재려면** `node wonja/eonje-doljji-jaenda.mjs`. 그 도구는 **한 판짜리**(본판) 자리를 고르게
돼 있다. light 처럼 **하루 여러 판**은 그 표의 「남은몫」 열을 보고 **바닥 구간(11~15시)을 피해**
나누는 것이 지금의 방법이다. 도구를 늘리지 않았다.
