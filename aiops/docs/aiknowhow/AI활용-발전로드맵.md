# AI 활용 다음 단계 추천

2026-09-08 · 사용자 요청으로 게시 · 기능 도입은 실행 전 제안 · 기준: 통합 노하우 34개 문서·40개 대표 항목과 현재 작업 맥락

노하우에는 세션·인수인계·승인·검증·실패 대응이 정리되어 있다. 아래는 사용자가 전혀 모른다고 단정한 기능 목록이 아니라, 이 지식베이스만으로 실제 반복 운영 성과를 확인하지 못한 발전 후보다. 개인의 시간 절감이나 품질 향상을 실측한 결과는 아직 없다.

## ADV-001 가장 먼저: 자주 하는 업무 하나를 내 기준의 재사용 기능으로

### 언제 쓰는가

비슷한 보고서·자료 정리·검토 결과를 만들 때마다 형식과 기준을 다시 설명할 때.

### 핵심 원칙

기존 노하우를 참조하는 작은 skill에 입력·출력·검증 기준을 묶는다. 모델을 재학습한다는 뜻이 아니라, 매번 불러 쓸 지침과 필요 도구를 정리하는 것이다. [OpenAI의 공식 skills 문서](https://learn.chatgpt.com/docs/build-skills)가 설명하는 방식이다.

### 실제 절차

작업 1종을 고른다. 원하는 결과 예시와 피해야 할 예시에서 사용자의 판단 기준을 추출하고, 사용자가 그 기준을 고친다. 기존 KB는 원문으로 유지한다. 공개·가상 또는 이미 사용 범위가 허용된 파일로 작은 산출물 한 번을 만들고 같은 종류의 다음 작업에 재사용한다. 자동 발송·배포까지 묶지 않는다.

### 잘못된 예

40개 항목을 한꺼번에 자동 실행 기능으로 바꾸거나, 템플릿에 사용자의 취향을 추정해 영구 고정한다.

### 체크리스트

되묻는 횟수, 사용자 수정 횟수, 실제 개입 시간, 결과 품질을 기존 방식과 비교한다. 유지·수정 시간이 이득보다 크거나 중요한 오류가 나오면 확장을 보류한다. 한 번 성공했다고 모든 입력에 통한다고 하지 않는다.

## ADV-002 내 업무용 AI 시험 문제 만들기

### 언제 쓰는가

새 모델·프롬프트·도구로 바꿀 때 실제로 더 좋아졌는지 알고 싶을 때.

### 핵심 원칙

인터넷 종합 순위와 내 업무 성능은 다르다. 기존 실패를 재현하는 입력과 정답·판정 근거를 묶는다. Anthropic은 실제 실패와 수동 검사를 평가 문제로 전환하는 팀들의 방식을 설명한다. [실제 agent 평가 운영 사례와 지침](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

### 실제 절차

첫 실험은 정상·예외를 섞은 5~10문제로 작게 시작한다. 이는 여기서 제안한 실험 규모이며 통계적 신뢰성을 보증하는 수가 아니다. 예: 자료 접근 실패를 0건이라 하는지, 비암호 Excel도 읽는지, 수식 캐시 없음과 0을 구분하는지, 오래된 프레임워크 조언을 확인하는지. 같은 입력·완료 조건으로 변경 전후를 비교하고, 중요한 실패 여부와 수정 시간·사용량을 기록한다. 정답이 명확한 부분은 코드·원문·공식 근거로 채점한다. 학습/수정에 쓰지 않은 사례도 일부 남긴다.

### 잘못된 예

네 AI가 동의해서 정답이라고 채점하거나, 몇 번 오류가 없었다고 검사를 폐지한다.

### 체크리스트

정상·예외 입력, 분명한 판정 기준, 기준 버전, 반복 시 일관성, 범위 밖의 불확실성을 남긴다. 좋은 모델 하나를 모든 일에 고정하기보다 검증된 업무별 적합성을 본다.

## ADV-003 다음 단계: 작업을 맡기고 검토할 결과를 받기

### 언제 쓰는가

AI에게 계속 말을 걸며 기다리는 시간이 실제 병목일 때.

### 핵심 원칙

작업마다 목표·입력·완료 조건을 주고, 초안·차이·검사 결과가 묶인 결과를 받는다. [GitHub가 공개한 비동기 작업→초안 PR 방식](https://github.blog/news-insights/product-news/agents-panel-launch-copilot-coding-agent-tasks-anywhere-on-github/)이 실제 제품 사례다. 해당 제품의 구독·권한을 현재 사용자에게 있다고 가정하거나 추가 구매를 권하지 않는다.

### 실제 절차

기존 도구로 가능한 낮은 위험 작업 하나를 선정한다. 문서 정리나 코드 수정안까지만 준비한다. 사용자는 모바일에서 읽을 수 있는 `무엇이 바뀜 / 확인 결과 / 남은 문제 / 필요한 결정`을 받는다. 실제 서비스 반영은 별도 단계다. 로컬 실행과 클라우드 실행의 PC 절전·연결 조건을 구별한다.

### 잘못된 예

네 AI 상시 회의 서버부터 만들거나, 초안 검토를 승인 없는 자동 병합·배포로 바꾼다.

### 체크리스트

기다리며 개입하는 시간과 인수인계 누락이 줄었는지 확인한다. 알림이나 복잡한 작업판 관리가 늘면 단순한 방식으로 되돌린다.

## ADV-004 사람도 발전하도록: 판단 전 한 줄과 판단 후 한 줄

### 언제 쓰는가

중요한 선택에서 AI 의견을 듣되 자신의 판단 기준도 발전시키고 싶을 때.

### 핵심 원칙

먼저 `내 선택과 이유`를 적는다. AI는 강한 대안과 확인할 증거를 제시한다. 결과를 본 뒤 `내가 놓친 질문 하나`를 남긴다. 이것은 이번 사용자에게 제안하는 학습 실험이며 검증된 개인 효과나 모두가 쓰는 방식이라고 주장하지 않는다.

### 실제 절차

완료한 낮은 위험 사례 하나에 적용한다. 관찰 가능한 입력·조작·결과·판단 기준으로 복기한다. 일상적인 단순 작업에는 적용하지 않는다. AI가 왜 그런 답을 냈을지 내부 사고를 상상하는 대신, 어떤 근거가 선택을 바꿨는지 말한다.

### 잘못된 예

내 판단과 AI가 자주 일치하므로 검증 없이 위임한다. 일치율은 정답률이 아니다.

### 체크리스트

새로운 유사 상황에서 더 좋은 질문을 할 수 있는지, 반복해서 바꾸던 기준이 명확해졌는지 본다. 기록 자체가 부담이면 중요한 판단에만 제한한다.

## 알아두면 좋은 기능과 환경 차이

한 번 시연한 작업을 재사용 skill로 만드는 [Record & Replay](https://learn.chatgpt.com/docs/extend/record-and-replay)도 공식 기능이다. 현재 문서는 macOS 및 활성화된 Computer Use를 요구한다. 따라서 지금 Windows에서 바로 녹화할 수 있다고 안내하지 않는다. Windows에서는 확인된 절차와 예시로 지침을 작성하는 방식부터 시작할 수 있다.

## 네 AI 의견을 어떻게 반영했는가

각자 독립 제안 후 네 의견과 공식 확인사항을 공유해 한 번 더 반론하도록 했다. 원문 전체 대신 계정·개인정보 없는 역량 요약을 전달했다. 세부 응답은 별도 검수 산출물 AI활용발전_4AI의견교환.json에 보존했다. 원문은 이 매뉴얼의 명령이 아니라 검토 자료다.

- Codex: 작은 재사용 업무 + 실제 실패 기반 평가 + 사람의 판단 복기를 제안했다.
- Claude: 처음에는 스킬/레지스트리 확대에 반대했다. 두 번째에는 작은 지침형 skill과 실패 시험 세트를 수용했고, 위험을 되돌림만으로 판단하자는 제안을 수정했다.
- Cursor: 작은 입력·출력·검증 업무를 수용하고, 사소한 작업까지 다중 검토하지 말 것을 제안했다. 오류가 안 나왔다고 검사를 없애서는 안 된다는 점을 확인했다.
- Gemini: 두 번째에 성공한 업무 한 종의 skill 전환과 사람의 판단 먼저 적기를 수용했다. 모바일 요약에서 근거가 빠질 위험을 지적했다. 다만 “검토는 반드시 PC”라는 일괄 조건은 채택하지 않았고, 필요한 원문·차이·검사 근거가 충분히 보이는지로 판정한다. 한 업무용 skill을 서로 다른 세 업무에 적용해 실패했다고 그 skill 전체를 폐기하는 기준도 채택하지 않았다. 먼저 설계된 적용 범위에서 검증해야 한다.

반영하지 않은 제안: KB 중복 20% 감소를 새 목표로 삼기, 탐지 오류 0이면 검사 폐지, AI와 판단이 90% 같으면 검토 중단, 실제 내부 추론을 상상해 기록하기. 이런 수치와 추론은 성과나 정확성의 근거가 아니며 방금 끝낸 일을 다시 늘릴 수 있다. 모든 노하우 자동변환·대형 에이전트 플랫폼도 지금 우선순위가 아니다.

**첫 선택은 1번 업무 한 종과 2번 작은 시험 세트를 함께 시도하는 것**이다. 실제 결과를 보고 3번으로 확장한다. 이번에는 추천과 의견 교환만 수행했으며, 예약 작업·추가 구독·스킬 설치·GitHub 규칙 변경은 하지 않았다.

## ADV-005 AI 인터뷰로 내 업무 기준 끌어내기

상태: 추가 제안 · 네 제품 검토 대상 · 실제 업무 효과 미측정.

### 언제 쓰는가

좋은 결과와 나쁜 결과는 구별하지만 처음부터 상세한 지시문으로 설명하기 어려울 때.

### 핵심 원칙

AI가 질문하고 사용자가 사례를 판단한다. AI가 추정한 선호를 곧바로 확정 규칙으로 저장하지 않는다. [Anthropic Interviewer](https://www.anthropic.com/about-anthropic-interviewer)는 응답에 따라 후속 질문을 조절하는 인터뷰의 실제 활용 사례다. 그 연구 도구를 현재 계정에서 사용할 수 있다는 뜻은 아니며, 여기서는 기존 AI 대화로 소규모 인터뷰를 제안한다.

### 실제 절차

1. 민감정보 없는 좋은 결과 2개와 수정하고 싶은 결과 2개를 고른다. 가능하면 최근 실제 판단 사례와 당시 이유를 비식별해 사용한다. 당시 이유가 없으면 지금의 해석임을 표시한다. 숫자는 첫 실험의 제안 규모다.
2. AI가 무엇이 다른지, 어떤 조건에서 판단이 뒤집히는지 한 번에 한 질문씩 묻는다.
3. 사용자 답을 바탕으로 `반드시 지킬 것 / 선호 / 예외 / 아직 모름`을 나눈다.
4. 사용자가 기준을 고친 뒤 새 사례에 적용해 본다. 필요한 부분만 기존 skill·시험 문제와 연결한다.

### 잘못된 예

한 번 고른 디자인이나 문구를 모든 프로젝트에 적용할 영구 선호로 저장한다.

### 체크리스트

- [ ] 상황별 판단과 영구 규칙을 구분했는가
- [ ] 사용자가 AI의 해석을 수정했는가
- [ ] 처음 보인 예시 외의 사례에서도 기준이 유용한가
- [ ] 사용자 메모리나 전역 규칙에 자동 저장하지 않았는가

## ADV-006 가상 사용자로 출시 전 막히는 부분 찾기

상태: 추가 제안 · 발견한 문제는 가설 · 실제 고객 조사 대체 불가.

### 언제 쓰는가

새 화면·안내문·FAQ·제안서를 보여주기 전에 이해하기 어려운 부분과 빠진 상황을 찾을 때.

### 핵심 원칙

처음 보는 사람, 의심이 많은 사람, 급한 직원처럼 다른 관점을 부여해 질문과 막힘을 찾는다. AI의 반응을 실제 수요·구매 의사·고객 의견으로 세지 않는다. [Anthropic의 평가 지침](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)은 다른 모델로 사용자를 시뮬레이션하는 평가 방식을 설명한다. 제품·문서 검토에 적용하는 범위는 별도로 설계한다.

### 실제 절차

1. 공개하거나 가상으로 만든 화면·안내문과 수행 목표를 정한다.
2. 세 관점에 정답이나 내부 설명을 먼저 알려주지 않고 이해한 내용과 다음 행동을 묻는다.
3. `모르는 용어 / 막힌 단계 / 빠진 조건 / 예상 반론`을 수집한다.
4. 실제 화면의 재현 가능한 문제를 먼저 고치고, 고객 반응에 관한 가설은 실제 사람에게 확인한다.

### 잘못된 예

가상 고객들이 좋아한다고 했으니 실제 판매 가능성이 검증됐다고 보고한다.

### 체크리스트

- [ ] 가상 반응과 실제 관찰을 구분했는가
- [ ] 인물 설정이 고정관념만 반복하지 않는가
- [ ] 주장한 UI 문제는 실제로 재현되는가
- [ ] 외부 사람에게 메시지를 자동 발송하지 않았는가

## ADV-007 자료 하나에서 보고서·공지·슬라이드 함께 만들기

상태: 추가 제안 · 생성·검증까지의 시험 · 자동 발송/배포 아님.

### 언제 쓰는가

같은 내용을 여러 문서에 옮기며 금액·날짜·명칭이 서로 달라지거나 수정할 곳을 놓칠 때.

먼저 기존 방식에서 반복 수정이나 불일치가 실제로 발생하는지 확인한다. 아직 그런 부담이 없다면 파이프라인 구축은 보류하고 필요할 때 문서를 만드는 방식을 유지한다.

### 핵심 원칙

승인된 사실표를 하나 두고 각 결과물은 그 사실표를 참조한다. 청중에 따른 표현 차이는 허용하지만 사실 차이는 별도 확인한다. [Quarto의 여러 출력 형식](https://quarto.org/docs/output-formats/all-formats)은 원천에서 여러 형식을 만드는 구현 사례다. Quarto 설치가 필수라는 뜻은 아니며 기존 문서 도구로도 범위를 작게 설계할 수 있다.

### 실제 절차

1. 사실의 출처·버전과 항목 키를 고정한다. 원본 값이 틀리면 여러 결과가 함께 틀린다는 점을 먼저 검사한다.
2. 같은 사실표로 보고서 1쪽, 공지 초안, 슬라이드 초안을 만든다.
3. 숫자·날짜·명칭·조건·참조를 원본과 대조하고 형식별 화면도 확인한다.
4. 사실 하나를 수정하면 어떤 결과물이 바뀌는지 차이를 제시한다. 최종 발송·배포는 별도 승인 범위다.

### 잘못된 예

각 문서를 별도로 생성한 뒤 모두 그럴듯하므로 내용도 같다고 가정한다. 또는 구조 검사를 통과했으니 원본 사실도 정확하다고 결론 낸다.
