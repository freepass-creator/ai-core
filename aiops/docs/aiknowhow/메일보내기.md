## 언제 쓰는가

기존 메일 연결로 본문·첨부를 준비하고 승인된 수신자에게 발송할 때 사용합니다.

## 핵심 원칙

기존 연결과 도구를 먼저 확인합니다. 메일을 보낼 수 있는 권한이 있다는 사실은 이번 발송 승인과 다릅니다. 수신자·제목·본문·첨부를 완성한 뒤 정확한 발송 범위의 승인을 확인합니다.

과거 SMTP 도구가 있었다는 이유로 현재 계정·앱 비밀번호 정책을 단정하지 않습니다. 사용자의 현재 Workspace 정본 연결을 우선 확인합니다.

## 실제 절차

1. 지정 계정과 기존 커넥터/메일 도구를 확인합니다. 로컬 스크립트는 현재 도움말과 코드를 읽어 기본값이 실제 발송인지 DRY RUN인지 먼저 확인합니다.
2. 수신·참조·숨은참조, 발신 표시명, 제목, 본문 파일, 첨부의 최종 버전을 준비합니다. 계정과 표시명은 별개입니다.
3. 긴 본문은 지원되는 body-file/stdin 또는 구조화 인자로 전달합니다. 여러 첨부·참조 인자의 지원 형식은 현재 도구 규격으로 확인합니다.
4. DRY RUN 결과에서 주소와 첨부를 확인합니다. 승인 전에는 실제 발송 플래그를 붙이지 않습니다.
5. 자격증명은 보호된 연결에서 읽고 값은 프롬프트·인자·로그·Git에 넣지 않습니다. 환경변수 이름을 적는 것과 값의 안전한 보관은 별개입니다.
6. 승인한 대상과 내용이 같을 때 발송하고 message ID·보낸편지함 등 실제 결과를 확인합니다. SMTP 접수와 최종 배달은 다르므로 접수만 확인했다면 그렇게 보고합니다.
7. 오류 뒤 재시도하기 전 보낸편지함과 중복 발송 가능성을 확인합니다. 발송 이력에는 비밀값과 불필요한 원문을 남기지 않습니다.

과거 기존 SMTP 도구를 찾지 않고 도메인 전체 위임부터 요청해 시간을 낭비한 사례가 있었습니다. 기존 수단 탐색은 보존하되, 위임이 필요한 조건은 계정·관리 정책·작업 요구별로 판단합니다. 읽기는 [메일읽기](메일읽기.md)를 봅니다.

## 잘못된 예

- 기존 연결을 확인하지 않고 관리자 위임을 먼저 확대합니다.
- 문서의 예시 발신 계정을 현재 정본으로 사용합니다.
- 첨부가 바뀐 뒤 이전 승인을 재사용합니다.
- timeout 뒤 같은 메일을 바로 다시 보냅니다.

## 현재 확인된 수단 (2026-09-09 실제 발송으로 확인)

- 도구: `C:/dev/mailtool/send_mail.py` — `--to`(여러 번) `--cc` `--subject` `--body-file`(UTF-8) `--attach`(여러 번) `--from-name` `--dry-run`
- **기본값이 실제 발송이다.** `--dry-run`을 붙여야 미리보기다. 승인 전에는 반드시 붙인다.
- 자격증명은 환경변수 `GMAIL_ADDRESS` / `GMAIL_APP_PASSWORD`에서 읽는다. **값은 어디에도 적지 않는다.** 있는지만 확인하려면 존재 여부(bool)만 출력한다.
- 호출 예는 `C:/dev/aiops/scripts/메일보고.mjs`에 있다(본문을 파일로 만들어 `--body-file`로 넘기는 방식).

### 함정 — 콘솔 인코딩 때문에 발송이 실패한 것처럼 보인다

Windows 기본 콘솔(cp949)에서는 **본문 미리보기를 출력하는 단계**에서 `UnicodeEncodeError: 'cp949' codec can't encode character '\u2014'`(줄표 등)가 나며 죽는다. 메일 자체의 문제가 아니라 **print 단계의 문제**다.

- 해결: `PYTHONIOENCODING=utf-8`을 지정하고 실행한다.
- 이때도 수신자·제목·첨부 줄은 이미 출력된 뒤이므로, **그 세 줄이 맞게 찍혔는지로 DRY RUN 검증은 할 수 있다.**
- 관련: [한글·Windows 셸 함정](한글로-코딩-함정.md)
