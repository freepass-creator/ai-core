# AI와 함께 만드는 ERP — 협업 운영층 제안 · Codex · 2026-08-31

## 목표

각 AI 세션이 독립적으로 맡은 일을 하되, ERP 정본을 바꾸기 전에는 같은 작업 상태·결정 근거·영향 범위·다음 행동을 확인한다. AI 답변이나 임시 파일이 ERP 사실을 대신하지 않는다.

## 현재 구현 가능한 최소 구조

1. 작업대장(`.coordination/tasks`)은 작업 ID·revision·상태의 정본으로 유지한다.
2. 로컬 미리보기는 작업대장을 읽어 비식별 `decision_id`, 상태, 근거 포인터, 안전 필터된 영향 경로만 만든다.
3. `DRAFT`는 검토·승인이 필요하다는 표시일 뿐 실행 권한이 아니다.
4. 취소는 대체가 아니다. 후속 결정이 확인될 때만 별도 `SUPERSEDED` 전이를 기록한다.
5. ERP·Sheet·Drive·Firestore에는 이 미리보기에서 쓰기 경로가 없다.

## 세션 충돌을 보는 기준

- **잠재 중복**: 아직 실행하지 않는 DRAFT/대기 작업까지 포함해 같은 파일 또는 쓰기성 리소스를 선언한 경우다. 설계 조정·작업 병합 후보로 본다.
- **실행 중 충돌**: 예약·분석·검토·적용 상태의 작업끼리 같은 파일 또는 쓰기성 리소스를 잡은 경우다. 실행 전 중지·revision 확인·담당 조정이 필요하다.
- `read:` 리소스를 함께 읽는 것은 충돌로 취급하지 않는다. 읽기 공유는 협업의 정상 경로다.

## 세션 인계 패킷

각 AI가 전체 작업대장을 다시 읽는 대신, 수신 역할에 필요한 비식별 작업 카드만 만든다. 카드에는 작업 ID·비식별 제목·등급·현재 revision·상태·검토 필요 여부만 포함한다. `DRAFT`의 카드는 검토 요청이지 승인 증거가 아니며, 새 revision이 생기면 이전 검토를 재사용하지 않는다.

세션을 새로 시작하거나 재개할 때는 작업 ID를 지정한 시작 브리핑을 먼저 만든다. 브리핑에는 해당 작업의 현재 revision·상태·리소스·잠재 중복 작업·필수 다음 절차만 넣는다. 따라서 새 세션이 전체 원문과 모든 과거 대화를 다시 읽지 않아도 현재 작업의 안전 경계를 확인할 수 있다.

## 신규 오더 없는 자율 진행 (DRAFT)

각 세션은 새 오더를 임의로 만들기보다, 시작 시 작업대장·시작 브리핑·자율 실행 카드를 읽고 현재 작업의 다음 안전한 행동을 이어간다.

- `SAFE_VERIFY`: 결정론적 로컬/읽기 전용 검증과 증적 보고를 계속한다.
- `CONTINUE_DECLARED_SCOPE`: 선언된 읽기·DRY RUN 범위에서만 이어가며, 원본 신선도를 다시 확인한다.
- `WAIT_DESIGN`·`WAIT_USER_APPROVAL`: 증적·질문·초안 정리까지만 하며, 구현·실행·범위 확대를 하지 않는다.
- `NO_ACTION`: 종료 작업을 되살리거나 같은 일을 새 오더로 복제하지 않는다.
- 자율 카드는 승인·권한·새 리소스를 만들어 내지 않는다. 새 외부 변경이나 정본 변경이 필요하면 기존 보호 절차로 되돌린다.

## AI ERP 제안 봉투

AI가 ERP에 대해 내는 결과는 자연어 지시가 아니라 `proposal_id`, 작업 ID·revision, 도메인, 근거 포인터, 선행조건, 제안 행동, 승인 수준을 가진 비식별 제안 봉투로 전달한다.

- `READ_ANALYSIS`: 읽기 분석 결과. 정본 변경 권한이 없다.
- `WRITE_REQUEST`: 변경 요청일 뿐 실행 명령이 아니다. `DESIGN_FINAL_USER_REQUIRED`와 `dry_run_only: true`가 없으면 거부한다.
- 근거는 원문 복사가 아닌 정본·검증 산출물 포인터만 사용한다.
- 승인된 실제 반영은 별도 작업 revision·실행 계획·재조회 검증을 거쳐야 하며, 제안 봉투 자체가 승인이 될 수 없다.

## AI ERP 제어 루프

도메인별 AI 작업은 다음 상태 전이만 허용한다.

```text
FACT_SNAPSHOT → CANDIDATE → EXCEPTION/PROPOSAL → APPROVAL_PENDING
→ APPROVED → APPLY_PLAN → APPLIED
```

- 사실 스냅샷은 원본의 기준시각·버전·근거 포인터를 고정한다.
- 후보는 결론이 아니라 검토 대상이다. 근거 부족·다중 후보·경계 위반은 `EXCEPTION`으로 보낸다.
- `CANDIDATE → APPLIED` 같은 승인 우회 전이는 금지한다.
- `APPLY_PLAN`은 실행 전 계획이며, 실제 반영 후에는 원본 재조회·검증 결과를 다시 연결한다.
- `APPLY_PLAN` 직전에는 승인된 사실 스냅샷 hash와 현재 원본 hash, 승인 revision과 현재 작업 revision을 모두 대조한다. 하나라도 다르면 반영하지 않고 새 후보·검토로 되돌린다.
- 승인은 제안 봉투 hash·명령 hash·대상 리소스·입력 revision·읽기 의존성 hash에 결속한다. 하나라도 바뀌면 DESIGN·FINAL·사용자 승인은 모두 무효다.
- 단순 열람과 판정에 사용한 읽기를 구분한다. 판정 읽기 의존성이 바뀌면 후보를 폐기하고 재생성한다.
- 실제 반영은 대상별 사전조건·idempotency key·부분 성공 상태·반영 영수증·사후 hash 검증을 가져야 한다. 자동 재시도는 하지 않는다.

## 필수 인계 필드

역할 간 인계에는 `입력 revision`, `결정`, `근거`, `가정`, `미확인`, `변경 대상`, `검증 결과`, `남은 위험`을 최소 필드로 둔다. 결과만 전달해 다음 세션이 승인 범위나 불확실성을 잃는 일을 막는다.

## ERP 작업 흐름

```text
ERP 사실/원본 → 읽기·후보 생성 → AI 독립 검토 → 결정 매니페스트
                                              ↓
                                  사람/정본 검증·승인
                                              ↓
                                  승인된 단위만 실제 반영
                                              ↓
                                  재조회·검증·결과 기록
```

## 단계적 적용

- 단계 A: 현재처럼 읽기 전용 협업 현황·결정 포인터를 만들고, 중복·충돌·대기 작업을 드러낸다.
- 단계 A-UI: `erp-uiux/codex/ai-erp-협업관제-목업.html`에 작업·제안·계약 예외·안전 규칙을 보여 주는 정적 목업을 둔다. 실제 데이터 fetch·ERP 쓰기·기존 FINAL 화면 변경은 금지한다.
- 단계 B: Claude DESIGN 후 중앙 매니페스트 저장 위치와 상태 전이 권한을 확정한다.
- 단계 C: 계약·수납처럼 고위험 도메인은 후보/예외/승인/반영을 별도 사건으로 남긴다.
- 단계 D: 충분한 재현 테스트 뒤에만 다른 ERP 도메인으로 확장한다.

## 수용 기준

- 같은 작업 revision의 현재 결정은 하나여야 한다.
- 어떤 세션도 `DRAFT` 또는 AI 추천만으로 ERP 사실을 변경할 수 없다.
- 민감 원문·토큰·연락처·거래 상세가 매니페스트에 들어가지 않는다.
- 결정의 근거·영향·차단 이유·다음 행동을 다른 세션이 원문 없이 찾을 수 있다.
- 반영 전후 원본 재조회와 결정론적 검증 결과가 연결된다.
- 협업 건강검사에서 작업 ID·revision 중복·민감 경로 선언·실행 중 충돌이 없어야 한다. 계획 단계의 잠재 중복은 실패가 아니라 조정 신호로 별도 보고한다.

## Claude DESIGN 요청

결정 매니페스트의 중앙 위치·권한·상태 전이·보존 기간, 역할별 인계 패킷의 허용 필드, AI ERP 제안 봉투의 승인 경계를 보호 구조로 확정해 달라. 승인 전에는 로컬 읽기 전용 미리보기와 DRY RUN 제안으로만 운용한다.
