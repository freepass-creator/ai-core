# 무엇이 「구조」이고 무엇이 「업무」인가

2026-08-20 사장님: 「코덱스가 구조는 못 바꿔도 **업무는 설계할 수 있어야** 한다. 업무 매뉴얼화는 괜찮다」

실행하는 쪽이 절차를 제일 잘 안다. 그래서 **이미 승인된 업무 절차(SOP)의 세부 순서·체크리스트는 코덱스가 직접 쓰고 고친다.**
구조는 한 번 틀리면 원본이 깨지고 되돌리기 어려우므로 Claude 설계 검토를 거친다.

SOP가 새 트리거·권한·리소스·라이브 쓰기 경로를 만들거나 바꾸면 더 이상 단순 SOP 수정이 아니라 구조(C등급)다. 실제 외부 쓰기는 SOP에 적혀 있어도 항상 D등급 승인 절차를 따른다.

## 코덱스가 스스로 (Claude 승인 없이)

| 무엇 | 예 |
|---|---|
| **업무 매뉴얼(SOP)** 작성·개선 | `docs/sop/*.md` — 통장 반영 순서, 파일 분류 순서, 월말 마감 순서 |
| 실행 순서·체크리스트·예외 처리 | 「6616 통장이 비면 8월 수납을 덮지 말고 보류한다」 |
| 기존 승인 SOP 안의 작업 스크립트 세부 | `jageum/*.mjs`, `drive/*.mjs`, `sheets/*-sync.mjs` 안의 절차 부분. 쓰기 대상·명령·권한을 넓히면 구조 |
| 판정 함수의 **세부 조건** | nav-sync 의 「프라임 보험이 0건이면 남은 것에 넣는다」 같은 조건식 |
| 실행 결과 보고·로그 | `docs/LOG.md`, 작업보드 상태 전이 |
| 직원 안내 문구의 다듬기 | 「받아서 → 여기에 올려주세요」 문장 손보기 |

## Claude 설계 검토가 필요한 것 (구조)

| 무엇 | 왜 |
|---|---|
| **시트 열·탭 구조** (추가·삭제·이름) | 열 하나가 밀리면 원본이 깨진다(2026-08-19 사고). `sheets/nav-spec.mjs` 포함 |
| **판정 기준 자체** | 「무엇을 문제로 볼 것인가」 — 미수·무보험·검사만료의 정의. 세부 조건은 코덱스, 정의는 Claude |
| **공용 라이브러리·제어 스크립트** | `lib/*`, `scripts/with-lease.mjs`. 여기가 흔들리면 전부 흔들린다 |
| **역할·권한·정책 문서** | CONTROL_PLANE · ROLES · AI_GUIDE · CLAUDE/AGENTS/GEMINI · lease 정책 |
| **직원이 하는 일의 범위** | 「직원은 올리기와 완료·코멘트뿐」 같은 원칙 |
| 데이터 원본을 지우거나 대량 이동 | 되돌리기 어렵다 — 사용자 승인도 함께 |

**애매하면 구조로 본다.** 판단이 갈리면 DRAFT 로 올리고 물어본다 — 막는 게 목적이 아니라 되돌릴 수 없는 것만 한 번 더 보자는 것이다.

## 업무 매뉴얼(SOP) 쓰는 자리

```
docs/sop/
  통장반영.md        은행 파일 → 계좌내역 → 입금내역 → 수납
  파일분류.md        00_미분류자료 → 번호 폴더 (file-in)
  직원시트갱신.md     nav-sync 로 범위·기간 다시 쓰기
  월말마감.md        (코덱스가 만들 것)
```

**SOP 한 장에 들어갈 것** — 이 형식만 지키면 내용은 코덱스 마음대로:
1. 언제 하나 (매일 아침 / 파일이 오면 / 매월 5일)
2. 무엇을 확인하고 시작하나 (선행 조건 · 막혀 있으면 하지 말 것)
3. 순서 (명령 그대로)
4. 끝나고 확인 (숫자가 맞는지 어떻게 아나)
5. 이럴 땐 멈춘다 (예외 · 사람에게 물어볼 것)

SOP를 바꾸면 `docs/LOG.md`에 한 줄 남긴다. 기존 승인 SOP의 세부 개선은 Codex가 처리하고, 새 흐름·등급·트리거·리소스가 생기면 먼저 Claude DESIGN을 받는다.
