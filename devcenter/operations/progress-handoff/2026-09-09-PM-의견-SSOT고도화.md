## 먼저 — 엔진은 이미 좋다

오늘 적대적으로 반례를 짜서 돌렸고 거짓 PASS는 **둘**밖에 못 찾았다(식별자 위생 · 사본 동일성).
둘 다 한 시간 안에 닫혔고, 내 반례 스크립트를 새 빌드에 다시 돌려 확인했다.
이 정도로 방어적인 v0.1은 흔치 않다. 아래는 「더 촘촘하게」가 아니라 **「방향을 바꾸자」**는 이야기다.

## ① 가장 중요한 것 — 검사 항목이 아니라 «분모»가 문제다

오늘 실측한 숫자다.

```
업무 등록부 (ssot/registry.json)        0건
  실제 원자 (aiops/lib/wonja/*.json)  201개
  판정 규칙 (aiops/wonja/*.mjs)       406개

규격 등록부 (devcenter/registry.json)  14건
  실제 git 저장소                      48개
```

**엔진은 지금 201개 중 0개를 검사하고 있다.**
등록부가 비어서 HOLD가 나는 건 정직하고 맞다. 문제는 그다음이다 —
원자 5개를 등록하고 PASS가 뜨면, 사람은 그것을 **「정본이 맞다」**로 읽는다.
보고서에는 `registered_count: 5`가 있지만 **「201개 중 5개」라는 말이 없다.**

대표가 겪은 문제는 「틀린 답」이 아니었다. **「세션마다 다른 답」**이었다.
그 원인은 세션마다 «세는 범위»가 달라서다. **분모를 안 박으면 엔진이 바로 그 문제를 못 막는다.**

### 제안 — 새 개념이 아니다. 이미 있는 것을 한 층 위로 올리는 것이다

사본에 이미 `coverage: full | subset`이 있다. 「정본 전체를 덮나, 일부만 덮나」를 **선언**하게 하고
어긋나면 잡는 구조다. 같은 것을 **등록부 자체**에 적용하면 된다.

```jsonc
{
  "version": 1,
  "universe": {                       // ★이 등록부가 «무엇 중» 몇 개를 덮는다고 선언하는가
    "kind": "glob",
    "locator": "aiops/lib/wonja/*.json",
    "coverage": "subset",             // full 이면 하나라도 빠지면 FAIL
    "확인한때": "2026-09-09"
  },
  "datasets": [ ... ]
}
```

보고서 맨 위에 이렇게 나와야 한다.

```
status: PASS
범위:   201개 중 5개 등록 · 196개 미등록          ← ★이 줄이 없으면 PASS는 오해를 부른다
```

그리고 판정 규칙:

| 관찰 | 판정 |
|---|---|
| `universe` 선언이 아예 없다 | **HOLD** — 「무엇 중 몇 개인지 모른다」 |
| `coverage: full` 인데 빠진 것이 있다 | **FAIL** — 전부 덮는다고 선언했는데 아니다 |
| `coverage: subset` 이고 미등록이 있다 | **PASS + `미등록 N건` 을 status 옆에 박는다** |

`coverage: subset`에 하한이 없는 문제는 내 2차 검토 C-5로 이미 올려 뒀다. 여기서 같이 풀린다.

**이것이 「완벽하게」의 실제 내용이라고 본다.** 검사를 촘촘히 하는 것보다,
**엔진이 자기가 안 본 것의 크기를 스스로 말하게 하는 것**이 먼저다.

## ② 아직 열려 있는 판정 문제 둘 (내 2차 검토에서 남은 것)

### C-3 — 신뢰 게이트가 과잉이다

```
if (target not in loaded or not trusted_sources[did] or not trusted_sources[target] ...)
                            ^^^^^^^^^^^^^^^^^^^^^^^^ 이 절
```

1차 수정의 취지는 **「기준 정본이 미검증이면 소비자를 탓하지 마라」**였고 그건 `target` 게이트다.
`did`(소비자 자신)까지 확장하면서, 소비자에게 소견이 **하나라도** 있으면 그 소비자의 참조 검사가 통째로 보류된다.

재현(내 `counterexamples.py` C-3):

```
자식에 필수값 1건 누락 + 깨진 FK 2건  →  BROKEN_REFERENCE 0건
같은 파일, 행만 깨끗하게              →  BROKEN_REFERENCE 정상 보고
```

1행의 이름 누락은 2행의 `vehicle_id`가 정본에 있는지와 **아무 상관이 없다.**
거짓 PASS는 안 만들지만(상태는 FAIL/HOLD 유지), 잃는 것은 **대표가 실제로 봐야 할 소견**이다.
미수·계약처럼 수천 행짜리 표에서는 한 행의 결측이 그 표의 모든 참조 위반을 가린다.

**의견:** `target` 게이트는 유지하고, 소비자 자신에 대해서는
**파일 수준 근거가 의심스러울 때(`FILE_AGE`·`SOURCE_CHANGED`)만** 보류한다. 행 내용 결함은 보류 사유에서 뺀다.
`CSV_STRUCTURE`·`MISSING_COLUMNS`는 이미 `continue`로 빠지므로 이 경로에 오지 않는다.

### C-4 — 엔진이 자기 정책과 모순된다

`comparison_policy` 한 줄 안에 두 말이 같이 있다.

- "Exact Unicode strings; no trimming…"
- "Blank/whitespace-only is null; no other null tokens."

```
정본 001,        사본 001,"   "   →  REPLICA_VALUES FAIL
```

`blank()`는 기본키·필수값·nullable 참조에서 이미 「빈 값과 공백만 있는 값은 같은 null」로 쓰인다.
**사본 비교에서만 둘을 다른 값으로 본다.**

**의견:** null끼리는 같게 본다. `blank()`가 이미 엔진의 null 정의이니 그게 일관된다.
null이 아닌 값의 정확 비교(`001` ≠ `1`)는 그대로 둔다.
반대로 정한다면 `comparison_policy` 문구를 고쳐라. **어느 쪽이든 코드와 문서가 같은 말을 해야 한다.**
이건 기술 판단이 아니라 정책 결정이라, 정하고 «적는» 것이 핵심이다.

## ③ 이미 있는 기능을 안 쓰고 있다 — `max_age_hours`

오늘 `aiops/docs/저장소지도.md`가 **10일 낡은 채로** 있었다. 44라고 적혀 있었고 실제는 68이었다.
다시 세는 도구(`scripts/저장소.mjs`)도 있었다. **아무도 안 돌렸을 뿐이다.**

`max_age_hours`는 이미 엔진에 있다. 파일 mtime만 본다는 한계도 이미 정직하게 문서화돼 있다.
그 한계에도 불구하고 **「열흘간 아무도 안 봤다」는 잡혔을 것이다.**

**의견:** 지도·규격처럼 «사람이 갱신해야 하는» 등록 항목에는 `max_age_hours`를 걸어라.
새로 만들 것이 없다. 등록부에 한 줄 더하는 일이다.

## ④ 잘한 것 하나 — 그 습관을 엔진 안으로 넣어라

`ssot/knowledge/source-manifest.json`에 이 문장이 있다.

> "Working tree contains modified and untracked knowledge files.
>  **Hashes identify the actual files read, not clean HEAD contents.**"

오늘 본 것 중 제일 값지다. 「깨끗한 커밋이 아니라 작업본을 읽었다」를 **스스로 밝힌 것**이다.
숨겼으면 아무도 몰랐다. 그리고 그 정직함 덕에, 병합이 끝나면 해시를 다시 떠야 한다는 걸 다음 사람이 안다.

**의견:** 그 습관을 사람이 쓰는 문장이 아니라 **엔진의 필드**로 만들어라.
모든 판정에 「무엇을 근거로 그렇게 말하는가」가 붙어야 한다.
`evidence`에 해시·행수는 이미 있다. 거기에 **「이 근거가 확정본인가 작업본인가」**가 빠져 있다.

## ⑤ 하지 말았으면 하는 것 — 검사 항목 늘리기 경쟁

오늘 2차 검토에서 세 AI가 「거짓 PASS 확정」이라고 내놓은 것이 **재현에서 전부 무너졌다.**
실제로 확인된 거짓 PASS 2건은 정적 판독이 아니라 **실행**에서 나왔다.
그리고 3차 파트 구성 논의에서는 셋이 만장일치로 제안한 것이 **이미 있는 것**이었다.

**항목을 늘릴수록 좋아지지 않는다.** 늘릴 때마다 「이것도 검사한다」가 늘고,
그만큼 PASS가 더 무거워 보이는데 정작 분모는 그대로다. 그게 제일 위험한 방향이다.

우선순위를 이렇게 본다. **① 분모 → ② C-3·C-4 → ③ max_age_hours → 그다음이 새 검사 항목이다.**

## 마지막 — 「완벽하게」가 무슨 뜻인지에 대해

이 엔진은 완벽해질 수 없고, 그렇게 설계된 것이 맞다고 본다.
`README`가 이미 그렇게 적어 뒀다 — 「사람이 정본을 올바르게 지정했는지까지 자동 보증할 수 없다」.

그러니 목표는 **틀리지 않는 것**이 아니라 **자기가 모르는 것의 크기를 정확히 말하는 것**이어야 한다.
HOLD가 이 엔진에서 제일 중요한 판정인 이유가 그거다.

오늘 하루 이 엔진에 대해 배운 것을 한 줄로 줄이면 이렇다 —
**PASS를 더 믿음직하게 만들지 말고, PASS가 무엇에 대한 것인지 더 정확하게 말하게 하라.**
