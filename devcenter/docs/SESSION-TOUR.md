# 다른 세션을 위한 개발센터 견학

목표는 읽을 문서를 늘리는 것이 아니라, 이번 작업에서 정본을 찾고 기존 자산을 선택하고 확인한 근거를 남기는 것이다. 이 안내는 docs/BASELINE.md의 적용 동선이며 새 규격이나 합격 기준이 아니다. 대상 프로젝트의 지침과 승인된 원본을 함께 확인한다.

## 1. 이번 작업의 정본을 찾는다

전체 규격 찾기에서 대상 프로젝트와 주제를 검색한다. registry.json과 node 틀.mjs <scope>로 원본 위치를 확인하고, 실제 원문과 현재 버전을 읽는다. 원본 경로·scope·브랜치/커밋 또는 작업 트리 변경 상태를 작업 기록에 남긴다. 검색 결과나 경로 존재만으로 현행 규격임을 확정하지 않는다.

참조: docs/BASELINE.md B01~B04, docs/CURRENT-STANDARDS.md. 원문에 접근할 수 없다면 해당 판단은 미확인으로 남긴다.

## 2. 만들기 전에 기존 것을 직접 써본다

선택할 부품의 입력·상태·의존성·사용처를 먼저 읽는다. 원자 실험실에서 이번 작업과 관련된 버튼·입력·표·박스를 조작하고 사용 코드와 원본 코드를 비교한다. CSS 스타일 창고에서 같은 프로젝트의 토큰과 스타일을 찾고, 재사용할 위치와 이유를 적는다. 맞는 자산이 없으면 찾아본 범위와 부족한 기능을 적고 신규 후보로 남긴다. 프로젝트 간 차이가 있다는 사실은 같은 프로젝트 안에서 새 변종을 만드는 근거가 아니다.

참조: docs/BASELINE.md B03/B06/B07, design/components/CATALOG.md, design/patterns/RESPONSIVE-SHELL.md. 원본 프로젝트용 예제가 다른 프로젝트에서도 바로 동작한다고 가정하지 않는다.

기능 창고에서는 프로젝트와 그룹을 골라 기존 처리 함수·API·계산·검증의 입력 표기, 반환 표기, 원본과 참조 파일을 확인한다. 선언 발견과 실제 사용은 구분한다. capabilities/IMPROVEMENTS.md에서 알려진 부족·오류·수정 상태도 확인한다.

## 3. 반례 하나를 해결해 본다

상황 A: 두 프로젝트의 버튼 높이가 다르다. 바로 한 값으로 덮을 수 있는가? 두 프로필의 적용 범위와 승인 원본부터 확인한다. 값이 다르다는 사실만으로 오류나 통합 대상으로 판정하지 않는다.

상황 B: CSS 두 파일의 해시가 같다. 하나를 지워도 되는가? 동일 내용은 중복 후보의 증거다. 소비 경로·적용 순서·책임 범위를 확인하기 전에는 삭제나 통합 근거가 되지 않는다.

상황 C: 데모에서 저장 버튼이 눌린다. 기능 완료인가? 예시 화면의 반응과 실제 저장·실패·권한 처리를 구분한다. 이번 작업의 완료 조건에 필요한 실행 증거를 확보한다.

충돌과 확인 과제 화면에서 실제 발견 사례를 하나 고르고, 원문·재현·로그 중 무엇으로 판단할지 적는다. 새 AI의 확신이나 다수 의견을 원본 증거 대신 쓰지 않는다.

## 4. 돌아갈 프로젝트에 적용할 계획을 남긴다

docs/BASELINE.md의 「바로 사용하는 작업 시작 양식」에 이번 작업을 채운다. 최소한 정본 위치와 버전, 재사용할 자산, 신규 제작이 필요한 이유, 확인할 상태와 증거가 구체적이어야 한다. 파일 이름만 나열하거나 모든 항목에 확인 완료라고 쓰는 것은 근거가 아니다.

작업 규모와 위험에 맞춰 해당 프로젝트의 검토 규칙을 따른다. 견학은 대상 프로젝트 수정·운영 배포·권한 변경을 추가로 허가하지 않는다. 다른 프로젝트의 지침 파일을 견학 과정에서 자동 수정하지 않는다.

## 5. 작업 후 다음 세션이 쓸 수 있게 돌려놓는다

최종 변경 버전, 실제 실행한 확인, 미확인·실패 항목과 다음 조치를 대상 프로젝트의 기존 작업 기록에 남기고, 인계 답변에 그 기록의 경로를 적는다. 기존 기록 위치가 없으면 센터의 runs/<task_id>/에 로컬 기록을 남긴다. runs는 Git 업로드 제외이므로 다른 환경의 세션에 자동 공유되지는 않는다. 공유 인계에는 비민감 요약과 접근 가능한 원본 포인터를 사용한다.

재사용 가능한 개선을 찾았다면 원본 위치와 적용 범위를 제안한다. 규격 내용의 새 사본을 만들지 않는다. 의미가 다른 규격의 통합은 후보로 남긴다. 작업 중 원본 버전이 바뀌면 영향을 다시 확인하고, 오래된 색인만으로 현재 기준을 판단하지 않는다.

참조: docs/IMPROVEMENT-REPORT.md, docs/FOUR-AI-WORKFLOW.md, AGENTS.md. SSOT 검증파트의 검수 범위와 예외는 ssot/PART.md를 따른다. 문서를 읽거나 버튼을 누른 것만으로 학습 완료·검수 통과를 자동 부여하지 않는다.

## 다른 세션에 전달할 요청

이번 개발에 들어가기 전에 C:/dev/devcenter/AGENTS.md와 C:/dev/devcenter/docs/SESSION-TOUR.md를 읽어줘. 원격 환경에서는 freepass-creator/devcenter 저장소의 같은 파일을 확인해줘. 접근 불가한 원본은 추정하지 말고 미확인으로 남겨줘.

내가 요청한 프로젝트와 작업 범위에 해당하는 규격·원자를 찾아 실제 원문과 현재 버전을 확인하고, docs/BASELINE.md의 작업 시작 양식에 정본, 재사용할 자산, 신규 제작 이유, 충돌·예외, 실행할 검증을 채워줘. 관련 없는 전체 프로젝트를 훑지는 말고, 이 견학으로 바뀐 구현 선택을 근거와 함께 짧게 설명한 뒤 승인된 작업을 진행해줘.
