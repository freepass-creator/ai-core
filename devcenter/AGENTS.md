## 처음 방문한 세션

이번 작업에 해당하는 [견학 안내](docs/SESSION-TOUR.md)를 읽고 기존 [기본 규격의 작업 시작 양식](docs/BASELINE.md)에 정본·재사용 자산·신규 제작 이유·검증 계획을 남긴다. 이 안내는 기존 규격을 찾아 적용하는 동선이며 정본 우선순위나 검수 정족수를 새로 정의하지 않는다. 대상 프로젝트의 승인 범위 안에서 수행한다.

대표(2026-09-09): 「**클로드 코덱스 커서 제미나이가 모두 참여해서 하는데 너한테 PM 주고 싶은거지**」

**PM = Claude Code.** 다만 PM은 «판단하는 자리»가 아니라 «범위를 정하고 충돌을 드러내는 자리»다.
어느 규격이 정본인지는 **대표님과 원본이 정한다.** PM이 정하면 그 순간 이 센터가 또 하나의 의견이 된다.

분담은 새로 만들지 않는다. `freepasserp4/AGENTS.md`에서 이미 운영 중인 것을 그대로 쓴다.

| | 개발센터에서 하는 일 | 하지 않는 일 |
|---|---|---|
| **Claude Code (PM)** | 범위·scope 확정 제안, 규격 충돌 판정, 게이트, 반례 제시 | 대량 구현·전수 수집을 직접 하지 않는다(오더로 넘긴다). 정본을 임의로 확정하지 않는다 |
| **Codex** | 구현, 어댑터, 반례 재현, 회귀 테스트, 의견 통합과 최종 책임 | 혼자 핵심 판정을 확정하지 않는다 |
| **Cursor Agent** | 흩어진 규격 수집·정리(노가다), 포인터 실제 연결, 정적 분석·회귀 누락 | 설계·보안 판단을 하지 않는다 |
| **Gemini CLI** | 데이터 구조·참조·사본 관계·중복 규격 탐지 | — |

## 7 Hub 라우팅

Development Center의 공식 전문 실행 영역은 Design / Data / Document / Engineering / Integration / Quality / Delivery **7개 Hub**다. 조직 정본은 `docs/HUB-ARCHITECTURE.md`, machine registry는 AI Core 루트 `registry/hubs.json`을 따른다.

모든 개발 요청은 작업 시작 시:
1. Primary Hub 1개를 지정한다.
2. 필요한 Secondary Hub를 연결한다.
3. AI Core 상위 Contract를 먼저 확인한다.
4. 각 Hub의 authoritative/candidate source를 구분한다.
5. 프로젝트 고유 정본을 Hub로 복제하지 않는다.
6. Quality Hub 검증과 필요한 경우 Delivery Hub runtime evidence까지 받아 완료를 주장한다.

예: “디자인 통일”은 Design Hub가 Primary, Quality Hub가 Secondary다. “Firebase 데이터 구조 변경”은 Data Hub가 Primary이고 Integration/Quality Hub가 함께 붙는다.

## 지킬 것

- **처음에는 서로의 결론을 보여주지 않고 독립 검토한다.** 이후 이견과 재현 증거를 전달해 조정한다.
- **판정 우선순위: 원본/요구사항 > 재현 테스트 > 실행 로그 > AI 추론/다수 의견.**
  AI 주장도 틀린다. 2026-09-09 SSOT 2차 검수에서 셋이 「거짓 PASS 확정」이라 한 것이 재현에서 전부 무너졌고,
  실제 결함 2건은 정적 판독이 아니라 **실행**에서 나왔다. 지적을 그대로 코드에 반영하지 않는다.
- **찾은 사람은 자기 건을 검증하지 않는다** (`freepasserp4/AGENTS.md` 2026-08-21).
- 검토 대상의 SHA-256, 각 검토 범위, 실제 응답, 반영·기각 이유를 남긴다.
  **수정 전 코드 검토를 수정본의 합격으로 옮겨 적지 않는다.**
- 네 역할 중 검토하지 못한 역할이 있으면 전체 상태는 **HOLD**로 남긴다. 다른 AI가 그 역할을 한 것으로 꾸미지 않는다.
- 설치·로그인·시스템 정책에 막히면 **실제 실패 내용을 기록**한다. 보호 정책을 우회하지 않는다.

## 지도점검 관제 (사용자 지정, 2026-09-09)

개발센터는 모든 개발의 작업 기준과 점검·시정·재검사 이력을 관장하는 작업대장이다. 어떤 AI의 개인 판단도 개발센터의 확정된 작업 범위·정본 포인터·검증 게이트를 임의로 건너뛸 수 없다.

- 흐름은 `대상 등록 → 정본·버전 고정 → 규격 점검 → 시정 배정 → 수정 실행 → 재검사·종결`이다.
- 규격 밖의 구현은 원본 경로·해시·위반 규칙·재현·수정 방법·재검사 방법을 갖춘 시정명령으로 남긴다.
- 이미 승인된 작업 범위 안의 수정은 개발센터가 담당 AI에게 배정하거나 직접 수행할 수 있다. 정본·권한·운영 데이터·배포를 바꾸는 수정은 대상과 범위를 직전에 다시 확인한다.
- 각 프로젝트의 업무 의미와 승인 원본은 제자리에 남는다. 개발센터는 개발 절차와 검증을 관장하며, 업무 원본을 복사해 새로운 정본으로 만들지 않는다.
- 수정한 역할과 최종 검수 역할을 분리하고, 수정본의 새 해시에서 원래 반례와 회귀검사를 다시 실행한다.

운영 규정의 정본은 [지도점검 규정](operations/inspection/POLICY.md)이다. 현재 공통 검사기는 읽기 전용 구조 점검과 시정 작업 패킷 생성까지 지원한다. 대상별 의미·UI·운영 연결은 어댑터가 붙은 범위만 검증한다.

## 이 센터에서 절대 하지 않는 것

1. **규격을 여기로 복사하지 않는다.** 가리키기만 한다. 복사하는 순간 정본이 둘이 된다.
2. **비슷하다는 이유로 두 규격을 합치지 않는다.** 합칠지 모르겠으면 `candidate`로 두고 HOLD로 남긴다.
3. **검증된 시정 근거와 승인된 작업 범위 없이 대상 프로젝트를 수정하지 않는다.** 먼저 의견·근거·재검사 방법을 남긴다.
4. **범위를 넓히는 제안은 변경 후보로 남기고** 대표님 확정 전에 구현 기준에 반영하지 않는다.
