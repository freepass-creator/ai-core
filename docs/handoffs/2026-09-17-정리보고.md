## 3. 「어디에 둘까」를 전부 닫았다

아침에 `/api/orders/:id/work` 는 **원천이 무슨 말을 하든 항상 HOLD** 였다. 주입구는 진작 뚫려 있었는데 **CLI 진입점이 아무것도 넘기지 않았다.**

배선하고 나서 재고를 세어 보니 **네 원천 중 실재하는 것이 하나뿐**이었다. 넷 다 닫았다.

| 원천 | 아침 | 지금 |
|---|---|---|
| **registry** | group 갈래에 묻힘 | **main + CI 검증** |
| **ledger** | 예시 5줄뿐 | **규약 — 오더 DB 옆** |
| **mappings** | 아무 데도 없음 | **규약 — 오더 DB 안** |
| **snapshot** | 생산자 없음 | **뼈대는 한 명령, 나머지는 선언** |

### ★ledger·mappings 를 «설정»이 아니라 «규약»으로 만든 이유

오더 기록과 원장/매핑이 **다른 설치에서 오면**, 형식 검사는 전부 통과하면서 **남의 설치의 업무를 말하는 투영**이 나온다. 경로를 각각 적게 두면 언젠가 하나만 바뀐다. 오더 저장소에 묶으면 **그 어긋남을 실수로 설정하는 것이 불가능**해진다.

### ★snapshot 은 「생산자 부재」가 아니라 「생산되는 물건이 아님」이었다

스냅샷이 담는 것 대부분 — 사용자가 intent 를 확인했는가, 약정의 주인이 누구고 기한이 언제인가, 실행이 허가됐는가, 관측이 언제까지 유효한가 — 은 **원장에도 git 에도 없다. 사람이 말해야 한다.**

그래서 생산자를 만드는 대신, 원장이 **진짜로 아는 셋**(어떤 항목이 있나·어느 프로젝트인가·어느 판본에서 관측됐나)만 파생하고 나머지는 **스키마 자신의 「아직 아님」 값**으로 둔다.

```
npm run control:derive <ledger.jsonl> <registry.json> <as-of>
```

파생본을 컨트롤타워에 넣으면 이렇게 나온다:

```
status HOLD | execution_authorized false
DEV-001  CONTROLLING_INTENT_UNCONFIRMED, MATERIAL_OBSERVATION_EXPIRED,
         COMMITMENT_NOT_ACTIVE, COMMITMENT_CONTROL_INCOMPLETE,
         AUTHORIZATION_REQUIRED, PROJECT_REVISION_STALE
```

**막는 이유 목록이 곧 「대표가 아직 갚아야 할 선언」의 목록이다.** 그것이 §1 의 **E** 다.

## 4. 오늘의 교훈 — **빨간불도 거짓말한다**

어제 정리한 것이 「초록불이 거짓말한다」였다. 오늘 그 **뒷면**이 나왔다.

`verify-main-state` 가 git 을 `core.quotepath` 기본값으로 불러, 한글 경로를 8진 이스케이프된 문자열로 받았다. 그래서 한글 이름 파일은 에피소드에 **올바르게 적어도 영원히 불일치**였고 `fileExists` 도 못 찾았다.

★**검사기가 빨간불을 내면 「대상이 틀렸다」로 바로 읽지 마라. 「검사기가 대상을 읽을 수 있는가」를 먼저 봐라.** 실수장부에 적었다(97→**98가지**).

### 함께 닫은 「거짓 초록」 둘

- **`registry:validate` 가 CI 에 없었다.** 스크립트는 진작 있었는데 워크플로가 부르지 않아, **INVALID registry 가 들어와도 아무도 몰랐을 것**이다
- **`ledger:verify` 가 없는 파일에 `VALID`/exit 0 을 냈다.** ENOENT 를 빈 문자열로 삼켰다 — **경로를 오타내도 초록**이었다

### ★「없는 것」과 「빈 것」을 다섯 자리에서 갈랐다

`WORK_SOURCE_MISSING_*` · `commands_absent_reason` · preflight 의 MISSING/INVALID/UNREADABLE · `LEDGER_FILE_MISSING` · `MAPPING_INVENTORY_ABSENT`.

근거는 매번 같다 — adapter 는 받은 목록에 줄이 없으면 **`UNLINKED` 라고 단정**한다. 무력화 시험에서 실제로 확인했다: 없는 매핑을 `[]` 로 읽게 하니 서버가 **`'UNLINKED'`** 를 답했다. **자료가 없어서 만들어진 자신 있는 오답**이다.

대표 계율 둘째 그대로다 — **「없다」가 아니라 「모른다」.**

## 5. 규칙을 «풀지 않고» 고친 한 건

registry 검증기가 ACTIVE 프로젝트에 `test`·`build` 를 둘 다 요구했다. 그런데 두 저장소의 `package.json` 을 직접 읽어 보니:

- **aiops** — 빌드 단계가 **원래 없다**(실행 스크립트 모음)
- **freepasserp4** — 단일 `test` 가 없다. `check:*` 가 **46개**이고 CI 가 개별 호출한다

**기록이 사실이고 규칙이 그 현실을 못 담았다.** 그래서 셋 다 하지 않았다 — 규칙 풀기 · 없는 명령 지어넣기 · 상태를 `HOLD` 로 바꿔 통과시키기.

대신 **맨 `null` 은 여전히 실패하고, 왜 없는지 적어야만 통과**하게 했다. 「그 단계가 원래 없다」와 「아직 아무도 안 만들었다」가 맨 null 로는 똑같이 보이기 때문이다. fp4 `#327` 에서 CI manifest 의 `manual`·`pending` 에 이유를 필수로 만든 것과 같은 모양이다.
