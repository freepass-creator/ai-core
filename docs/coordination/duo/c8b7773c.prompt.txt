상품 갱신 워치독 설계안 — 반례를 대라

배경: Claude 앱 예약작업 지킴이가 6일간 죽어 있었다. 회차 하나가 시작 7초 뒤 권한 승인 대기로 멈췄는데 status 가 running 으로 남아, 스케줄러가 '이미 도는 중'으로 보고 이후 44회를 아예 안 걸었다. 실패가 아니라 '안 끝남'이 전부를 막았다. 설계안 요지 다섯. (1) 워치독은 Claude 예약작업이 아니라 순수 PowerShell 무한 루프로 만든다 — 감시자가 감시 대상과 같은 병(승인 대기·사용량 한도·앱 닫힘)에 걸리면 안 되므로. 기존 검증된 kakao 워치독과 같은 구조, 최종 방어선은 Windows 시작프로그램. (2) 지킴이의 건강이 아니라 '발행 나이'를 본다 — 지킴이가 죽어도 GitHub 예약이 돌면 영업자에겐 문제가 없었다(실제로 그랬다). 증상을 본다. (3) 월~토 09~20시에 발행 나이 90분 초과면 알린다. 같은 발행판으로는 한 번만. (4) ★워치독은 워크플로를 걸지 않는다 — 쓰는 곳은 지킴이 하나로 유지. 이중 발행 위험과 지킴이 무의미화를 피하려는 것. (5) 멈춘 세션을 밖에서 죽이지 않고 사람에게 알리기만 한다. 묻는다. (가) (4)가 옳은가, 아니면 워치독이 지킴이와 같은 조건 검사를 거쳐 직접 걸어 자동 복구를 완성하는 게 나은가. (나) '발행 나이'만 보면 놓치는 고장이 있나. (다) 이 설계가 오늘 겪은 고장을 실제로 잡는가 — 잡지 못하는 경로가 있으면 대라. (라) 승인 규칙만 넣고 워치독은 안 만드는 선택이 더 나은가.
