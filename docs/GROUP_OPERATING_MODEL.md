# AI Core 그룹 운영 모델 v1.0

- 상태: `USER_CONFIRMED / ADOPTED_FOR_LOCAL_IMPLEMENTATION`
- 결정일: 2026-09-15 (KST)
- 목적: 로컬 작업자가 기존 GitHub·로컬 프로젝트를 AI Core 그룹 구조로 정리하고, 이후 생성되는 모든 프로젝트를 공통 규격으로 시작할 수 있게 한다.

## 1. 사용자 결정

AI Core는 모든 플랫폼의 코드를 한 저장소에 섞는 단일 애플리케이션이 아니다.

AI Core는 **그룹 본사**다. ERP, 영업 앱, 정산, 홈페이지, 법무, 콘텐츠 등은 **독립 자회사**로 관리한다. 다만 기획실·개발센터·경영지원·공통 연결·공통 검증처럼 여러 자회사가 함께 써야 하는 기능은 본사 공통 조직으로 합친다.

사용자는 원칙적으로 AI Core 프로젝트의 세션/섹션에서만 자연어로 오더한다. AI Core는 오더를 해당 자회사와 본사 공통 조직으로 배정하고, 진행·승인·검증·후속 상태를 공통 작업대장으로 관리한다.

## 2. 목표 토폴로지

```text
AI-CORE-GROUP/
├─ headquarters/
│  ├─ ai-core/                 대표 오더·판단·기억·배정·작업대장
│  ├─ planning-office/         요구사항·기획·프로젝트 설립
│  ├─ devcenter/               개발 규격·공통 자산·품질검사
│  ├─ management-support/      권한·문서·감사·인수인계
│  └─ shared-services/         공통 연결·계약·검증·배포 기반
│
└─ subsidiaries/
   ├─ freepass-erp/
   ├─ freepass-sales/
   ├─ fp-settlement/
   ├─ freepass-homepage/
   ├─ work-control/
   ├─ casemap/
   ├─ webtoon-studio/
   └─ future-projects/
```

### 저장소 원칙

- 위 구조는 **로컬 그룹 작업공간**의 구조다.
- 각 자회사 폴더는 원칙적으로 독립 GitHub 저장소와 독립 Git 이력을 유지한다.
- 각 자회사는 독립 빌드·테스트·릴리스·배포·롤백 경계를 가진다.
- 본사 공통 기능은 버전이 있는 패키지·계약·템플릿·검사기로 제공한다.
- 자회사는 공통 기능의 특정 버전/커밋을 고정해서 채택한다. `latest` 자동 추종은 금지한다.
- AI Core는 프로젝트별 정본을 복제하지 않고, 프로젝트 위치·revision·공통 기능 채택 상태를 등록한다.

| 구분 | 본사 공통 | 자회사 독립 |

| 오더 | 접수·분류·배정·진행·후속 | 프로젝트 내부 실행 |
| 기획 | 요구사항 형식·결정 기록·작업 패킷 | 사업 목적·고유 기능·우선순위 |
| 개발 | 기본 폴더·공통 계약·재사용 자산·검사 | 실제 제품 코드·도메인 로직 |
| 디자인 | 접근성·반응형·버튼/표/폼의 최소 품질 규격 | 브랜드·색상·폰트·분위기·화면 위계 |

| 배포 | 공통 배포 게이트·증거·복구 규칙 | 도메인·환경·릴리스 일정·운영 승인 |
| 문서 | 공통 문서 규격·템플릿·보관 규칙 | 프로젝트 전용 문서와 원본 |
| 기억 | 공통 실패·재사용 원칙·진행 포인터 | 프로젝트 사실·결정·고유 이력 |

## 4. 공통화 판정 규칙

다음 조건을 모두 만족할 때만 본사 공통 기능으로 승격한다.

1. 둘 이상의 프로젝트에서 실제로 반복 사용된다.
2. 입력·출력·의미·오류·부작용이 동일하거나 명시적 어댑터로 분리 가능하다.
3. 프로젝트 고유 브랜드나 업무 규칙을 강제로 섞지 않는다.
4. 독립 테스트와 버전 관리가 가능하다.
5. 원본 SSOT가 어느 프로젝트에 있는지 명확하다.
6. 공통화 전후의 동작 차이와 롤백 방법을 검증할 수 있다.

조건이 부족하면 프로젝트 로컬 기능으로 유지한다. 이름이 비슷하다는 이유만으로 합치지 않는다.

## 6. 자회사 독립 원칙

각 플랫폼·앱·홈페이지는 다음을 독립적으로 가져야 한다.

- 명확한 mission과 사용자
- 프로젝트 SSOT
- 독립 repository와 기본 branch
- 독립 데이터 저장소와 스키마
- 독립 브랜드·디자인 토큰
- 독립 실행·빌드·테스트 명령
- 독립 배포 대상과 도메인
- 독립 환경변수·권한
- 프로젝트 전용 요구사항·결정·실패 기록
- 독립 릴리스와 롤백

본사 규격 채택은 자회사의 고유 색깔을 제거하는 것이 아니다. 공통 규격은 **품질과 협업의 바닥선**이고, 사업·브랜드·사용자 경험은 자회사가 소유한다.

## 7. 신규 프로젝트 설립 규격

앞으로 만드는 모든 프로젝트는 최소한 다음을 가진다.

```text
project/
├─ PROJECT.md               목적·사용자·범위·비목표
├─ AGENTS.md                AI 작업 규칙과 금지사항
├─ project.json             기계 판독용 Project Capsule
├─ src/                     제품 코드
├─ tests/                   자동 검사
├─ docs/
│  ├─ SSOT.md               데이터·업무 정본
│  ├─ DECISIONS.md          주요 결정
│  ├─ HANDOFF.md            현재 상태·다음 작업
│  └─ RELEASE.md            배포·롤백
├─ contracts/               데이터/API/상태 계약
├─ brand/                   고유 디자인 토큰·브랜드 자산
├─ .env.example             비밀값 없는 환경변수 명세
└─ package/build config
```

필수 Project Capsule 필드:

- `project_id`
- `mission`
- `repository` / `default_branch`
- `status`: ACTIVE / REFERENCE / HOLD / RETIRE
- `stack` / `runtime`
- `install` / `dev` / `build` / `test`
- `source_roots`
- `authoritative_sources`
- `data_ssot`
- `deploy_targets`
- `required_approvals`
- `shared_capabilities`와 고정 revision
- `known_blockers`
- `last_verified_revision`

## 8. 기존 저장소 편입 절차

한꺼번에 구조를 뜯지 않는다. 프로젝트 하나씩 다음 절차로 편입한다.

1. **등록** — 저장소·로컬 경로·배포·DB·담당 기능을 그룹 registry에 등록한다.
2. **분류** — ACTIVE / REFERENCE / HOLD / RETIRE로 판정한다.
3. **원형 보존** — 현재 작동 상태와 Git 이력을 보존한 채 그룹 작업공간에 둔다.
4. **기준선 검증** — 현재 빌드·테스트·실행·화면·데이터 연결을 기록한다.
5. **정본 선언** — 데이터·업무 규칙·코드·배포의 실제 SSOT를 확정한다.
6. **규격 정리** — 폴더·명칭·환경변수·테스트·문서·인수인계를 공통 형식에 맞춘다.
7. **공통 후보 추출** — 실제 중복 기능만 본사 공통 서비스 후보로 올린다.
8. **어댑터 분리** — 프로젝트 고유 매핑·계정·필드를 공통 엔진과 분리한다.
9. **재검증** — 변경 전후 기능과 데이터 결과를 비교한다.
10. **전환** — 새 구조가 PASS한 후에만 기존 위치를 읽기 전용 또는 폐기한다.

편입 중 두 위치가 동시에 SSOT가 되지 않도록 각 단계에서 정본 위치와 revision을 기록한다.

## 9. 현재 프로젝트 적용 메모

- `freepass-creator/ai-core`: 그룹 본사 오더·기억·조정의 기준 저장소.
- `freepass-creator/devcenter`: 본사 개발센터 후보. 공통 규격·재사용·검증 기능을 유지·정리한다.
- `freepass-creator/aiops`: 분리 검토 대상.
  - Google·Drive·Sheet·인증·작업대장 등 범용 기능은 본사 공통 서비스 후보.
  - 과태료·자금·보험 등 업무 의미와 절차는 운영 도메인에 유지.
- ERP·영업·정산·홈페이지·법무·웹툰은 각각 독립 자회사로 관리한다.
- `jpkerp5`: 사용자 결정상 RETIRE/폐기 대상. 신규 통합 원천으로 사용하지 않는다.
- ERP 명칭:
  - ERP4는 플랫폼 이름.
  - ERP3는 Firebase ERP3를 뜻하며 신규 기준으로 사용하지 않는다.
  - ERP5는 Firebase ERP5를 뜻하며 원천 대조 후 데이터 SSOT로 사용한다.

## 10. 사용자 오더 흐름

`사용자 오더 → AI Core 접수 → 프로젝트/기능 식별 → 본사 공통 기능 선택 → 자회사 실행 → 검증 → 결과/후속 기록`

사용자는 저장소 이름·실행 도구·AI 이름을 매번 지정하지 않아도 된다. 답에 따라 결과가 달라지는 핵심 결정만 사용자에게 묻는다.

중요한 외부 변경은 기존 승인 경계를 유지한다. 문서 작성, 검증, 승인, 실제 배포·전송·데이터 변경, 현실 결과를 하나의 `완료` 상태로 합치지 않는다.

## 11. 로컬 1차 작업 순서

1. 로컬에 `AI-CORE-GROUP/headquarters`와 `subsidiaries` 골격을 만든다.
2. 각 기존 저장소는 독립 Git 상태를 유지한 채 해당 위치에 배치한다.
3. AI Core에 그룹 프로젝트 registry를 만든다.
4. 모든 저장소를 ACTIVE / REFERENCE / HOLD / RETIRE로 분류한다.
5. 현역 프로젝트마다 Project Capsule과 기준선 실행 결과를 만든다.
6. DevCenter를 본사 개발 표준·검증 조직으로 정리한다.
7. AIOPS에서 공통 연결과 운영 도메인 기능을 분류한다.
8. 첫 파일럿 자회사 하나를 공통 규격에 맞춰 편입한다.
9. 자연어 오더 → 해당 자회사 작업 패킷 생성 → 로컬 실행 → Proof Bundle 반환 흐름을 검증한다.
10. 파일럿 결과를 보고 공통 규격에서 불필요한 항목을 제거한다.

첫 파일럿은 운영 배포를 바꾸지 않는 현역 프로젝트로 선택한다.

## 12. 완료 기준

다음이 실제로 확인되어야 1차 그룹화 완료다.

- 새 세션이 AI Core 진입문서만 읽고 현재 프로젝트와 진행 작업을 찾을 수 있다.
- 사용자의 자연어 오더가 올바른 자회사와 공통 조직으로 배정된다.
- 각 자회사가 독립적으로 빌드·테스트·배포될 수 있다.
- 공통 기능은 버전/commit이 고정되어 있고 프로젝트별 채택 상태가 보인다.
- 공통 변경이 자회사 고유 브랜드·업무 규칙을 덮어쓰지 않는다.
- 프로젝트별 SSOT가 하나이며 중복 정본이 없다.
- 민감한 원본 데이터·인증정보가 그룹 공통 저장소에 복제되지 않는다.
- 실행 결과가 commit, 검사, 실패/생략, 남은 위험과 함께 반환된다.

## 13. 금지사항

- 모든 프로젝트 코드를 하나의 애플리케이션처럼 결합하지 않는다.
- 여러 저장소를 검증 없이 한꺼번에 이동하지 않는다.
- 이름이 비슷한 함수를 자동으로 공통화하지 않는다.
- 기존 `AGENTS.md`, 데이터 계약, 배포 규칙을 일괄 덮어쓰지 않는다.
- 공통 패키지를 `latest`로 자동 갱신하지 않는다.
- 프로젝트 고유 브랜드와 화면을 본사 UI로 획일화하지 않는다.
- 고객·직원·법무·금융 원문 또는 인증정보를 공통 Git 저장소에 복제하지 않는다.
- 기존 저장소 종료 전에 새 위치의 실행·검증·롤백을 확인하지 않는 일을 금지한다.
