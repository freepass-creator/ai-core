# Claude 인계 — AI Core 본사·자회사 통합

작성일: 2026-09-15 (Asia/Seoul) · 문서 버전: 1.0

**이 작업은 비상 기능 구현이 아니라, 기존 운영·개발 자산을 AI Core 본사와 독립 자회사 체계로 편입하는 작업이다.** 구조 원칙의 정본은 [그룹 운영 모델](GROUP_OPERATING_MODEL.md)이며, 이 문서는 그 결정을 로컬 실행자가 이어받기 위한 작업 인계안이다. 기존 결정을 다시 설계하거나 비상 판정기 `EMG-P0` 작업으로 바꾸지 않는다.

기록 기준선: `freepass-creator/ai-core@ca8215be9c3e2002c2e1ce37bb3e0b53592e1733`. 클로드는 시작 시 최신 원격과 실제 로컬 상태를 재조회한다. 이 인계서 저장은 로컬 통합 완료, 클로드 수신·실행 확인, 자동 배포 또는 운영 변경 승인을 의미하지 않는다.

## 1. 이미 확정된 방향 — 다시 선택받지 않는다

2026-09-15 그룹 운영 모델에서 확정한 원칙을 아래와 같이 상속한다.

- AI Core는 **본사**다. 대표의 오더, 공통 기억, 기획, 배정, 진행, 검증과 인수인계를 모은다.
- ERP·영업 앱·정산·홈페이지·법무·콘텐츠 등은 **독립 자회사**다. 플랫폼의 고유 기능·브랜드·업무 규칙·데이터는 별도로 관리한다.
- 단순히 저장소 링크만 연결하는 것이 아니라, 기존 프로젝트를 **하나씩 실제 로컬 그룹 작업공간에 배치하고 규격을 정리**한다.
- 그렇다고 모든 코드를 하나의 애플리케이션이나 단일 Git 이력으로 섞지 않는다. 저장소·SSOT·권한·빌드·릴리스·배포·롤백 경계를 보존한다.
- 기획실·개발센터·공통 연결·문서·검증 등 함께 쓸 것은 본사 공통으로 정리한다. 이름이 비슷하다는 이유만으로 합치지 않는다.
- 앞으로 만드는 프로젝트는 공통 생성 규격으로 시작하되 각 제품의 고유 색깔은 유지한다.

이번 인계서의 단계명·작업 ID·제출 경로는 위 결정을 실행하기 위한 세부안이다. 기존 사용자 결정과 새로운 구현 선택을 혼동하지 않는다.

## 2. 목표 구조와 공통화 경계

```text
AI-CORE-GROUP/                  로컬 작업공간; 전체 제품의 단일 Git 저장소가 아님
├─ headquarters/
│  ├─ ai-core/                  오더·기억·조정·작업대장
│  ├─ devcenter/                공통 개발 규격·재사용·품질검사
│  ├─ planning-office/          기획 공통 기능
│  ├─ management-support/       문서·권한·감사·인수인계 공통 기능
│  └─ shared-services/          연결·계약·검증 등 공통 기능
└─ subsidiaries/
   └─ <기존 프로젝트>/          프로젝트별 독립 Git·SSOT·데이터·배포 유지
```

이름은 운영 모델의 논리적 구분이다. 실제 경로·저장소 매핑을 먼저 확인한다. 기획실·경영지원마다 새 저장소를 자동 생성하지 않는다. 이미 맞는 자산이 있으면 재사용하고 필요한 경계만 만든다. 이 문서의 폴더 그림은 로컬에 생성됐다는 증거가 아니다.

| 대상 | 본사에 모을 것 | 프로젝트에 남길 것 |
|---|---|---|
| 기획·오더 | 요구사항 형식, 결정·작업·인계 규격 | 사업 목적, 고유 기능, 우선순위 |
| 개발·디자인 | 생성 규격, 재사용 계약, 버튼·표·폼 등의 최소 품질 기준 | 업무 로직, 브랜드, 색상, 화면 위계 |
| 연결·인증 | 연결 인터페이스, 검증 가능한 공통 어댑터 | 계정, 키, 접근 권한, 리소스 바인딩 |
| 데이터 | 의미·단위·ID·필드 정의 방식과 계약 | 원본 데이터, DB, 스키마와 업무 SSOT |
| 배포·문서 | 검증·복구·문서 템플릿·인계 규격 | 도메인, 운영 환경, 릴리스, 원본 문서 |
| 기억 | 검증된 공통 교훈과 프로젝트 포인터 | 프로젝트의 사실·결정·고유 이력 |

공통화는 운영 모델의 6가지 조건을 모두 확인한 경우에만 진행한다: 둘 이상 프로젝트의 실제 반복 사용, 의미·입출력·오류·부작용의 일치 또는 명시적 어댑터 분리, 고유 브랜드·규칙 보존, 독립 테스트·버전 관리, 원본 SSOT 식별, 전후 동작·롤백 검증. 부족하면 로컬 유지 또는 후보로만 기록한다. 채택은 버전/커밋 고정이며 `latest` 자동 추종은 하지 않는다.

## 4. 혼동하면 안 되는 프로젝트 메모

아래는 운영 모델의 결정이며, 현재 로컬 설치·가동을 조사한 결과가 아니다.

- `freepass-creator/ai-core`: 본사 오더·기억·조정의 기준 저장소.
- `freepass-creator/devcenter`: 본사 개발 규격·공통 자산·검증 기능의 정리 대상.
- `freepass-creator/aiops`: 통째로 없애거나 공통 폴더로 옮기지 않는다. Google·Drive·Sheet·인증·작업대장 등 범용 기능은 공통화 후보, 과태료·자금·보험 등 업무 의미·절차는 운영 도메인에 남긴다. 실제 이동·추출은 검증과 해당 프로젝트 승인 이후다.
- ERP4는 플랫폼 이름이고, ERP5는 Firebase ERP5다. ERP5의 데이터 SSOT는 **원천 대조 후** 판정하며, 통합을 이유로 DB 이전·데이터 수정까지 수행하지 않는다. ERP3를 새 기준으로 삼지 않는다.
- `jpkerp5`는 사용자 결정상 `RETIRE` 대상이다. 신규 통합 원천으로 쓰지 않되, 실제 저장소 삭제/Archive가 됐다고 가정하거나 이 작업에서 실행하지 않는다.
- 그 밖의 프로젝트는 실제 저장소와 배포·데이터 원천을 조회해 식별한다. 그림의 논리 이름을 실제 GitHub 저장소명으로 추측하지 않는다.

## 5. 첫 작업 GROUP-P0 — 원형 보존형 로컬 편입 파일럿

**목표: 현황을 정리하고 비운영 자회사 하나로 그룹 작업 흐름을 실제 검증한다. 전체 이전이나 새 프레임워크 설계가 첫 작업이 아니다.**

### A. 변경 전 조사

기존 정본·registry와 사용자가 지정한 로컬 개발 위치를 먼저 읽는다. 저장소별 원격 주소(자격증명 제거), 브랜치·HEAD, 미커밋/미추적 변경의 존재, worktree·실행자, 현재 경로, 배포·DB 연결의 참조, 기준선 검증과 미확인을 기록한다. 원문·비밀값을 수집·출력하거나 홈 디렉터리를 무차별 탐색하지 않는다.

ACTIVE / REFERENCE / HOLD / RETIRE는 기존 명시적 결정과 관측 근거로 분류한다. 분류 근거가 없으면 확인 대상으로 남기며, 오래됐거나 테스트가 없다는 이유만으로 폐기하지 않는다. 실행 중이거나 정본이 모호한 저장소는 해당 변경만 보류하고 다른 안전한 조사·준비를 계속한다.

### B. 작업공간과 registry 정리

확인한 경로 아래 `AI-CORE-GROUP/headquarters`와 `subsidiaries` 골격을 준비하되 기존 폴더를 덮어쓰지 않는다. 현재 registry/스키마/작업대장이 있는지 확인한 뒤 재사용 또는 최소 수정한다. 없을 때만 운영 모델의 Project Capsule 필드를 충족하는 얇은 registry를 만든다. 코드·업무 사실의 별도 SSOT를 만들지 않는다.

로컬 경로, 원래 정본 위치, 대상 경로, 실제 repository/default branch, 관측 revision, 채택된 공통 버전, 검증 결과와 미확인이 연결돼야 한다. 개인 경로·민감 배포 정보 등은 승인된 기록 범위로 제한한다.

### C. 자회사 하나만 원형 보존 편입

운영 배포를 바꾸지 않는 현역 프로젝트 하나를 근거를 들어 선택한다. 문서만 보고 특정 앱을 파일럿으로 확정하지 않는다. 전용 branch/worktree 또는 독립 clone 등 대상 상태에 맞는 방식을 택하고, 기존 Git 이력과 프로젝트 규칙을 유지한다.

원격 clone에는 로컬 미커밋 작업이 포함되지 않는다는 점을 확인한다. 미커밋·미추적·무시 파일·인증정보·캐시를 통째로 복사하지 말고, 누락/보존/재설정 항목을 구분한다. 공유 worktree의 브랜치 변경, 덮어쓰기, 일괄 staging, 강제 push, `reset --hard`, `clean`으로 정리하지 않는다.

첫 편입은 기존 실행 위치를 정본으로 유지하고 새 위치는 검증용으로 표시한다. 두 위치에서 동시에 운영 작업·스케줄러를 실행하지 않는다. 절대경로·환경설정·외부 작업의 경로 의존성을 점검하되 운영 연결은 임의 갱신하지 않는다.

### D. 기준선과 한 건의 작업 흐름 검증

기존·신규 위치의 같은 소스 revision을 비교한다. 설치·빌드·테스트 명령의 실제 내용을 먼저 읽고 배포/라이브 쓰기 부작용이 없는 검사만 격리 환경에서 실행한다. 실데이터나 비밀키가 필요하면 비식별 fixture 또는 검사 생략 사유를 사용하며, 생략을 PASS로 처리하지 않는다.

기존 PROJECT/SSOT/HANDOFF와 Capsule이 있으면 원문을 보존하고 포인터나 부족한 필드만 보완한다. 신규 프로젝트 표준을 기존 코드의 대규모 폴더 개편 명령으로 해석하지 않는다.

사용자가 요청한 실제 비운영 작업 한 건을 AI Core 오더 → 올바른 자회사/공통 기능 배정 → 작업 패킷 → 로컬 검사 → 증거 반환으로 연결한다. 해당 작업이 없으면 가짜 업무 성과를 만들지 말고 이 단계만 미검증으로 남긴다. 폴더 생성과 문서 작성만으로 그룹 운영 전체가 작동한다고 보고하지 않는다.

### E. 전환은 별도 판단

파일럿 전후 검증·SSOT 포인터·경로 의존성·롤백을 대조한 뒤 전환안을 낸다. 운영 경로·스케줄러·배포 변경, 기존 위치의 읽기 전용 전환·삭제·폐기는 별도 대상과 승인을 확인한다. 테스트 통과만으로 자동 실행하지 않는다. 첫 파일럿이 검증되기 전 다른 자회사를 일괄 이전하지 않는다.

## 6. 후속 단계 — 첫 작업과 섞지 않는다

GROUP-P1: 파일럿에서 확인한 규격으로 자회사를 하나씩 편입하고 불필요한 절차를 줄인다.

GROUP-P2: 실제 반복 사용되는 공통 기능만 DevCenter/본사 후보로 등록한다. 의미·부작용·권한 경계를 검토하고 어댑터와 고정 버전을 통해 단계적으로 채택한다. AIOps 보호 구조나 라이브 업무 변경은 해당 프로젝트의 검토·승인·실행자 규칙을 따른다.

GROUP-P3: 새 프로젝트 생성 규격을 검증된 최소 템플릿으로 정리한다. 자회사 브랜드·업무 로직을 본사 UI나 공통 엔진으로 일괄 교체하지 않는다.

## 7. 완료 증거와 클로드 반환 위치

첫 결과는 기존 인계/작업대장 위치를 우선 사용한다. 없을 때 사용할 제출 경로 제안은 `docs/handoffs/GROUP-P0-RESULT.md`다. 지금 그 결과 파일이 존재하거나 아래 검사가 통과했다는 뜻은 아니다.

| 반환 항목 | 필요한 내용 |
|---|---|
| 대상과 변경 | 저장소·브랜치·commit SHA, 편입 전후 경로, 변경 파일, 실제 source revision |
| 보존 | 기존 Git 이력·미커밋 작업·브랜드·SSOT·환경/배포 경계의 보존 근거 |
| registry·Capsule | 기존 자산 재사용/수정/신규 사유, 최신 소스 연결과 UNKNOWN 항목 |
| 실제 검사 | 명령·환경·PASS/FAIL/SKIP, 전후 비교, 검증 범위; 같은 SHA에 결속 |
| 작업 흐름 | 실제 비운영 요청과 패킷/실행/증거 연결 또는 해당 단계 미검증 사유 |
| 권한과 한계 | 운영 전환·데이터·배포·삭제 수행 여부, 승인 참조, 남은 위험과 중지 조건 |
| 다음 인계 | 다음 한 작업, 담당 수신 여부, 필요한 결정; 미확인 상태를 완료로 올리지 않음 |

문서 확인, 로컬 골격 생성, 저장소 편입, 검사 통과, 전환 승인, 실제 운영 전환을 각각 기록한다. 새 세션이 진입 문서만으로 현재 프로젝트·진행 작업·다음 작업을 찾는지도 별도로 확인한다. 자기검토와 독립 검토를 구분한다.

## 8. 대표가 클로드에게 전달할 시작 문구

> freepass-creator/ai-core의 최신 WORK_READ_FIRST.md와 docs/CLAUDE_GROUP_INTEGRATION_HANDOFF.md를 읽고 본사·자회사 통합을 이어가. docs/GROUP_OPERATING_MODEL.md의 확정 방향을 유지해. 기존 저장소를 하나씩 원형 보존해서 AI-CORE-GROUP에 편입하고, 공통은 본사로 정리하되 고유 앱·데이터·브랜드·배포는 독립 유지해. 첫 작업 GROUP-P0의 현황 조사·registry 정리·비운영 자회사 하나 파일럿부터 진행해. 기존 규격과 기능을 먼저 재사용하고, 실데이터·운영 배포·권한·삭제는 별도 승인 없이 하지 마. 실제 검사 결과와 commit, 미확인 사항, 다음 한 작업을 GitHub에 남겨. 비상 판정기 EMG-P0와 혼동하지 마.

## 9. 현재 인계 상태와 갱신 규칙

현재는 **합의 근거 확인 및 구현 인계 문서 작성 단계**다. 사용자 PC 확인·폴더 생성·저장소 이전·클로드 수신/실행·독립 검토·파일럿 검증은 이 문서 작성으로 수행되지 않았다.

클로드가 이어받으면 읽은 기준 commit과 자기 branch/worktree, 실제 조사/검사 결과를 남긴다. 새로운 충돌·사용자 변경 결정은 원출처와 함께 기록하고 필요한 경우 운영 모델을 별도 검토로 개정한다. 인계서에 서로 다른 정본을 누적하거나 기존 합의를 조용히 덮어쓰지 않는다.
