# AI Core — U/F/E/I Operating Model

★대표 2026-09-28: 「여기 고도화를 우리가 UFEI로 했었잖아. UFEI로 고도화를 할 수 있을까?」
   그리고 「어떤 구분값을 다 이렇게 **공백이 없게끔** 처리할 수 있는 방법으로 가야 될 것 같아」

정본은 `freepasserp4/docs/UFEI-OPERATING-MODEL.md` 다. 이 문서는 그 규율을 **ai-core 에 맞게 옮긴 것**이고,
lane 이 담는 내용만 다르다. 규율(정본은 main 하나 · 작업선은 짧게 회수 · 한 파일 한 소유자 · 5번째 lane 금지)은 그대로다.

## 왜 그대로 베끼지 않았나

freepasserp4 의 U/F/E/I 는 **화면 있는 consumer 제품의 계층**이다(`I 연결 → E 파생 → F 기능 → U 화면`).
ai-core 는 화면 제품이 아니라 **거버넌스·원장·등록부·도구**라, 그대로 쓰면 U 가 거의 빈다.
그래서 이름과 순서는 두고 **담는 것을 바꿨다.**

## 쓰기 전에 잰 것 (2026-09-28 실측)

수평(계층) 분할의 알려진 단점은 **「기능 하나가 여러 층을 거쳐 대기열이 생긴다」**이다. 그래서 먼저 쟀다.

```
최근 커밋 120개 중 lane 에 걸리는 71개
  한 lane 안에서 끝남   61  (86%)
  lane 을 가로지름      10  (14%)   ← 그중 6건이 F+I, 전부 「스크립트 + 그 검사」 모양
```

**86% 가 한 lane 안에서 끝난다.** ai-core 의 일은 실제로 층 모양이므로 수평 분할이 맞다.
가로지르던 F+I 6건은 규칙 A(검사는 대상의 lane 을 따른다)로 사라진다.

★**이 비율이 무너지면 분할을 다시 생각해야 한다.** 숫자가 반대였으면 UFEI 는 오답이었다.

## Lane

| Lane | 뜻 | 작업선 | 소유 |
|---|---|---|---|
| **I** | 연결 | `work/ai-core/i-01-integration` | 바깥과 닿는 자리 — 등록부, 다른 저장소 관측, 물리 사본의 신선도 |
| **E** | 엔진 | `work/ai-core/e-01-engine` | 결정 로직 — 라우팅, capability, 컨트롤타워, 작업 원장. 바깥을 모른다 |
| **F** | 규율 | `work/ai-core/f-01-discipline` | 일을 통과시키는 관문과 절차 — academy, reuse, canon guard, 브랜치 규율, main-state, 협업 채널 |
| **U** 🔒 | 정본 디자인 | `work/ai-core/u-01-design` | 디자인 토큰·컴포넌트·UI/UX 헌법 |

규칙:

- **A. 검사와 계약은 대상의 lane 을 따른다** — test/erp5-keeper.test.mjs 는 scripts/erp5-keeper.mjs 가 I 라서 I 다. 검사를 따로 떼면 한 작업이 늘 두 lane 을 건드린다(실측: 횡단 10건 중 6건이 이 모양이었다).
- **B. 사본은 I** — PROVENANCE.json 이 있는 자리는 개발하는 곳이 아니라 원본과 어긋났는지 «재검증»하는 곳이다. 그 일이 곧 그림자 신선도이고 I 의 책임이다.
- **C. 문서는 그 문서가 규율하는 lane** — 문서를 한 통에 몰면 그 통이 곧 공백이 된다.
- **D. 저장소 공용은 F** — package.json·.github 처럼 누구의 것도 아닌 것은 «기타»로 두지 않고 규율 lane 이 맡는다. 「기타」 통을 만들지 않는 것이 공백을 안 만드는 길이다.

우선순위: I → E → F → U

## 공백을 «고장»으로 만든다

초안을 재 보니 추적 파일 1,182개 중 **931개(78.8%)가 어느 lane 에도 안 걸렸다.**
지도를 잘 그리는 것으로는 안 된다 — 새 폴더가 생길 때마다 다시 벌어지고, 공백은 눈에 안 보이니 아무도 안 고친다.

```
node scripts/check-lane-coverage.mjs
  · lane 없는 파일이 하나라도 있으면 FAIL
  · 한 번도 이기지 못하는 «죽은 규칙»이 있으면 FAIL
  · --write-codeowners 로 .github/CODEOWNERS 와 이 문서의 표를 다시 만든다
```

- **정본은 `registry/lanes.json` 하나.** CODEOWNERS 와 이 문서의 표는 거기서 **생성**한다.
  따로 쓰면 어긋나고, **그 어긋남이 새 공백이다.**
- **검사에는 fallback 이 없다.** 「기타」 통을 두면 덮임이 공짜로 100% 가 되어 검사가 아무것도 증명하지 못한다.
- CODEOWNERS 맨 위의 포괄 줄은 목적이 다르다 — **리뷰어 없는 파일을 만들지 않기 위한 것**이다. 둘을 섞지 않는다.

### 겹침이 아니라 «죽은 규칙»을 막는다

처음엔 「두 규칙이 같은 파일을 주장하면 안 된다」로 두려 했다가 고쳤다.
좁은 규칙과 넓은 규칙은 **당연히** 겹친다(`^scripts/.*erp5-keeper` 와 `^scripts/`). 금지하면 부정 전방탐색 괴물이 된다.
`.gitignore` 도 CODEOWNERS 도 겹침을 허용하고 **순서**로 정한다.

그래서 지도는 **먼저 맞는 규칙이 이긴다**로 정하고, 대신 **한 번도 이기지 못하는 규칙**을 잡는다.
그런 줄은 **있지도 않은 분류가 사는 것처럼 보이게** 한다 — 공백의 다른 얼굴이다.
★넣자마자 두 줄이 걸렸다: `^src/work/`, `^src/control-tower/`. **그 폴더는 아예 없었다.**

## 소유

Codex 판단(2026-09-28): **축은 사람이 아니라 «변경 책임·파일 경계»다. 소유자는 영구 고정보다 «작업별 단일 책임자».**

- 한 시점에 **한 lane 은 한 사람**이 잡는다. Codex 든 Claude 든 lane 을 잡고 끝내고 놓는다.
- 같은 파일을 두 lane 이 동시에 고치지 않는다.
  ★2026-09-28 에 실제로 났다 — Claude 가 작업선에서 `duo.mjs` 를 고치는 동안 Codex 가 main 위로 재추출해 같은 파일을 고쳤고, 병합이 필요했다.
- **U 는 잠가 둔다.** 디자인 정본은 2026-09-14 브라우저 영수증으로 고정돼 있다.
  일이 없는 lane 을 열어 두면 **없는 일을 만들어 낸다**(Codex 가 든 「형식적 U」 반례). 실제 디자인 작업이 생길 때 연다.

## 하지 않는 것

- 임시 5번째 작업선, duplicate engine/adapter 를 만들지 않는다.
- lane 을 사람 이름으로 부르지 않는다(`gpt/…` 같은 actor 브랜치는 `check-branch-discipline` 이 이미 막는다).
- 브랜치를 오래 살려 두지 않는다. **검증이 끝나면 작게 회수한다.**
- Firebase RTDB 는 어떤 경우에도 쓰지 않는다.

## 이 모델이 «안» 고치는 것 (착각하지 말 것)

2026-09-28 하루에 실제로 아팠던 곳은 이랬다:

```
지킴이가 6일간 죽어 있었다
몇 주째 틀린 방아쇠를 당기고 있었다
정본에 「월~토 09~19시」라 적혀 있었다 (실제는 24시간 매시)
9/27 하루 11회가 전부 실패했다
```

**어느 것도 lane 으로 막히지 않는다.** 전부 「정본이 현실과 어긋난 걸 아무도 안 봤다」는 문제다.
UFEI 는 **쓰기 규율**이지 읽기 규율이 아니다.

→ 그래서 lane 마다 **정본 대조**를 하나씩 붙인다:
   **I** 등록부가 원격과 맞나 · **E** 판단이 실제 회차와 맞나 · **F** 관문이 실제로 막고 있나.
   쓰기만 정리하고 읽기를 그대로 두면, 틀린 것을 «깔끔하게» 쓰게 될 뿐이다.
