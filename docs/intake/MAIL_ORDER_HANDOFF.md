# 자료 조사 → 메일 준비 → 승인 → 발송 인계 계약 초안

**상태: 문서 설계만 작성. 실행 연결·발송 가능 여부·수락 사례는 미구현/미검증.** 자연어 접수 코드 `ba82f26265c5fccebdebf1f9368d584d70f95fb0`는 변경하지 않는다. 새 원장·인증·메일 도구를 정의하지 않는다.

메일 접수 시 먼저 [기존 연결 SSOT](../../memory/TOOL_CONNECTIONS.md)의 Mail connection reuse를 따른다. 기존 경로가 정상인 경우 설치·로그인을 생략하고 해당 연결을 재사용한다. 계정이 모호하거나 연결을 확인하지 못하면 발신자를 임의 선택하지 않는다. 자세한 관찰 범위는 [재사용 안내](MAIL_CONNECTION_REUSE.md)에 기록한다.

## 기준과 같은 업무의 경계

- PR20 `fe9315535e31a6edb723562b2b3515fcdf01107e`: `contracts/control-tower.schema.json`의 sources/authorization/evidence_receipts 및 `scripts/run-control-tower.mjs`. READY도 `execution_authorized: false`다.
- PR21 `21b1e16d2ab5b1b658e03275da5a5ad5515c8931`: `src/orders/store.mjs`의 intake/handoff와 `docs/ORDER_CONTROL_INTEGRATION.md`. 기존 인계 패킷은 `MANUAL_HANDOFF`, `automaticExecution: false`이며 발송 승인이 아니다.
- 사용자는 총괄에게 “자료를 찾아서 메일해줘”라고 말한다. 총괄이 검색 범위·대상·누락 정보를 확인하고 같은 `orderId`와 중앙 매핑된 `work_id`를 이어간다. 담당 AI·로컬/서버가 바뀌어도 새 오더나 별도 정본을 만들지 않는다. 두 ID는 서로 다른 식별자이며 그대로 대입하지 않는다. 기존 세부 작업 `taskId`로 책임을 구분하고, 필요 하위 업무 관계는 총괄의 기존 매핑 절차로만 연결한다.
- PR21의 claim/lease·report·close나 담당자 합의는 PR20의 실행 권한·완료 증거가 아니다. 연결되지 않은 업무는 UNLINKED로 남기고 발송/최종 완료를 막는다. 실제 상태 변경은 기존 정본 함수와 expectedHead를 사용하는 총괄 adapter 책임이다.

## 책임 인계

| 단계 | 책임과 넘기는 결과 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| 총괄 접수 | 원래 요청과 근거 메시지, 허용된 자료 검색 범위, 대상 후보, 미확정 사항 | “어느 자료를 누구에게 보낼까요?”처럼 필요한 내용만 질문. 이름만으로 주소를 추정하지 않는다. |
| 조사 담당 | 지정 범위의 정본 후보, ID·버전·관찰 시각·범위, 적합성/불일치/누락 요약 | 동명 후보가 있으면 선택 요청. 발견 메타데이터와 실제 원문 검토를 구분한다. |
| 메일 준비 담당 | 확정 후보를 기준으로 발신 계정·수신자·제목·본문·첨부의 검토 묶음과 DRY RUN 결과 | 사용자에게 읽을 수 있는 본문과 첨부 목록·변경점을 보여 준다. 전체 원문을 다른 AI에 자동 전달하지 않는다. |
| 총괄 확인/승인 | 해당 묶음 버전에 대한 사용자 직전 승인 근거 | 최초 “메일해줘”는 아직 특정하지 않은 수신자/본문/첨부의 최종 승인으로 확대하지 않는다. |

| 총괄 증거 확인 | 같은 발신 계정에서 SENT 재조회, 내용/첨부 대조와 근거 연결 | 발송 증거가 확인된 범위만 보고. SENT는 수신자의 배달·열람 증거가 아니다. |

이번 문서는 위 단계의 실제 검색·초안 생성·발송을 승인하거나 수행하지 않는다.

## 최소 인계 정보

아래는 **의미상 요구 정보**이며 새 JSON 스키마나 기존 패킷 필드 추가 구현이 아니다. 총괄이 기존 인계/근거 참조에 어떻게 연결할지 고정해야 한다. 누락값은 미확정으로 유지하고 기본 수신자·기한·완료조건을 만들지 않는다.

| 묶음 | 반드시 보존할 정보 |
|---|---|
| 업무 연결 | 기존 `orderId`, `orderVersion`, `requirementRevision`, `taskId`, 담당/다음 책임자; 중앙 매핑의 `work_id`, 검증된 `project_id`, `subject_revision`, 조회한 ledger head. 요구 버전·레코드 버전·Git 커밋·원장 head를 구분한다. 기존 lease 토큰/자격 증명은 복사하지 않는다. |
| 요청/조사 근거 | 원래 메시지 ID와 정확한 근거 구간, 허용 검색 범위, 파일 ID·원문 버전/수정 시각·관찰 시각·검토 범위, 후보 선정 근거와 미해결 사항. 프롬프트에는 필요한 비식별 요약만 전달한다. |
| 발송 검토 묶음 | 발신 계정/별칭, 정확한 To/Cc/Bcc, 제목, 본문 형식과 검토 가능한 내용/참조, 최종 본문 SHA-256, 첨부별 원본 ID·버전·파일명·형식·크기·최종 전송 바이트 SHA-256. 서명·링크·내보내기 형식까지 확정한 묶음 버전 및 전체 내용 digest. 민감한 주소/본문은 권한 있는 검토 화면에서만 표시한다. |
| 승인 연결 | 승인자와 원래 승인 메시지 참조·시각, 대상 묶음 digest/버전, 허용 발송 action/target/scope, 유효기간 또는 미확정 상태. PR20 authorization의 revision은 40자리 subject Git revision이며 메일 digest로 대체하지 않는다. 묶음과의 결합은 검증 가능한 승인 근거 참조로 고정하고 adapter 매핑이 없으면 HOLD다. |

PR20 sources의 ref/revision/observed_at/valid_until/status/severity 및 receipt의 id/kind/status/ref/revision/target/observed_at/digest는 기존 계약을 따른다. 메일 API 응답이나 조사 메모를 곧바로 PASS receipt로 복사하지 않는다. 검증 근거·종류·대상 커밋·범위의 연결은 adapter가 확인한다. SENT 대조에서 본문이나 첨부를 검증할 수 없는 항목은 부분 확인으로 남긴다.

## 변경과 응답 유실

1. 발송 직전 정본 업무, 승인, 수신자, 첨부 원본 버전과 최종 바이트를 다시 대조한다. 수신자/본문/제목/첨부/범위가 달라지면 기존 승인을 재사용하지 않고 변경된 검토 묶음으로 재승인을 받는다. 권한 만료·철회·요구 변경도 발송을 막는다. 파일명이나 동일 Drive ID는 같은 내용의 증거가 아니다.
2. 하나의 논리적 발송은 고정 식별자와 묶음 digest로 추적한다. 동일 요청의 재전달은 기존 결과를 조회한다. 기존 PR21 requestId 중복 처리나 PR20 eventId만으로 외부 메일의 exactly-once를 보장한다고 주장하지 않는다.
3. 발송 호출 후 응답 유실/시간초과가 나면 **발송 여부 불명, 재발송 보류**로 인계한다. 같은 발신 계정의 제공자 메시지 ID/검증 가능한 상관 근거로 SENT와 기존 시도를 대조한다. 제목/수신자만 같은 메일은 확정 근거가 아니다. 잠깐 검색되지 않았다는 이유로 미발송을 단정하지 않는다.
4. 이미 보낸 내용이 확인되면 발송을 반복하지 않고 기존 증거와 projection을 복구한다. 중복/불일치/확인 불가는 총괄에 올린다. 새 requestId나 재승인만으로 불명 시도의 재발송 안전성이 확보되지는 않는다. 제공자 재시도 보장이 실제 확인되지 않으면 자동 재시도를 막는다.
5. 원장 append 응답 유실은 동일 event ID와 페이로드를 정본에서 재조회하고, 중복 append를 맹목 재시도하지 않는다. head 충돌은 재조회·재평가한다. 메일 발송 성공 후 원장/화면 반영 실패도 다시 메일을 보내는 사유가 아니다. 두 저장소/메일 시스템 간 원자적 트랜잭션을 가정하지 않는다.
