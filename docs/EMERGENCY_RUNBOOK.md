# AI Core 비상매뉴얼

문서 버전: 0.1 · 작성일: 2026-09-15 (Asia/Seoul)

이 문서는 **공통 비상 진입점**이다. 프로젝트별 코드·데이터·계약·운영 SOP의 정본이나 승인 체계를 대체하지 않는다. 별도 브랜치에서는 검토안이며, main 반영 여부와 각 프로젝트의 운영 채택 여부는 따로 확인한다. 자동 감지·전역 잠금·롤백 프로그램을 구현했다는 뜻이 아니다.

## 0. 먼저 할 일 — 첫 화면

> **해당 작업의 추가 쓰기를 보류한다 → 무엇이 실제로 영향을 받았는지 확인한다 → 필요한 증거를 안전하게 보존한다 → 승인된 범위만 복구한다 → 실제 결과를 검증한 뒤 재개한다.**

| 순서 | 지금 할 일 | 완료로 인정할 증거 |
|---|---|---|
| 1. 보류 | 내가 추가로 실행할 관련 쓰기·배포·재시도를 보류한다. 다른 실행자에게는 중지를 요청한다. | 실제로 멈춘 작업과 응답 미확인 작업을 구분한 기록 |
| 2. 식별 | 프로젝트, 저장소, 브랜치/커밋, 환경, 영향을 받은 리소스, 마지막 정상 상태를 확인한다. | 현재 조회한 식별자·revision·관측 시각. 모르면 `UNKNOWN` |
| 3. 보존 | 비식별 오류, 변경 범위, 실행 기록과 백업의 안전한 위치를 보존한다. | 원문이 아닌 접근 제한된 증거 참조 |
| 4. 판단 | 아래 사고 유형을 고르고 책임자·단일 실행자·필요 승인을 확인한다. | 복구 계획과 아직 충족되지 않은 조건 |
| 5. 복구·검증 | 격리 환경 검증 후, 유효한 승인이 있는 대상만 변경하고 결과를 다시 조회한다. | 실행 결과와 같은 revision/환경에 묶인 검증 |

정상 서비스나 무관한 작업을 일괄 중단하지 않는다. 영향 범위를 모르면 **관련 가능성이 있는 변경을 보류**하고 읽기 진단으로 범위를 좁힌다. 전체 중단은 전체에 영향이 있다는 근거와 대상 운영 절차의 권한이 있을 때만 검토한다.

외부 작업 취소, 배포 중단, 계정·토큰 폐기, 접근 차단도 상태 변경이다. 현재 범위에 유효한 사전 승인 또는 직전 승인이 없다면 실행하지 않고 필요한 조치를 즉시 보고한다. 민감정보 노출이 계속되는 경우, 이미 승인된 최소 차단을 방대한 증거 수집 때문에 늦추지 않는다.

## 1. 언제 발동하는가

다음 중 하나라도 관측되면 관련 변경을 보류한다. 단순한 가능성과 실제 사고를 구분하며, 보류 자체는 사고 확정이 아니다.

- 원본과 결과가 다르거나, 데이터 삭제·오염·엉뚱한 대상 쓰기가 의심된다.
- 예상하지 않은 프로덕션 배포, 공개 URL/alias, 권한 변경 또는 비밀정보 노출이 보인다.
- 여러 AI가 같은 파일·브랜치·라이브 리소스를 수정하거나, 원격 revision이 달라졌다.
- 테스트 실패, 승인 만료, 범위 변경, lease 상실 또는 원본 변경이 발생했다.
- 어느 저장소·브랜치·문서·데이터가 정본인지 확인할 수 없다.
- 외부 쓰기 요청이 타임아웃됐거나 연결이 끊겨 성공 여부를 모른다. 실패로 단정하거나 재전송하지 않는다.

보고에는 [사고 기록 양식](INCIDENT_TEMPLATE.md)을 사용한다. 개인정보가 없는 참조만 해당 프로젝트의 허용된 기록 위치에 남긴다. 이번 문서 작성 자체를 실제 사고로 등록하지 않는다.

## 2. 권한과 정본

### 공통 원칙

- AI Core는 조정·기록을 맡는다. 실제 복구 대상과 해당 프로젝트의 정본은 원래 저장소/시스템에 남긴다.
- 사용자의 현재 지시는 의도와 요청 범위를 정한다. 기술 권한, 대상 식별, 필수 검토와 실행 승인은 별도로 확인한다. 요청이 모호하다고 전체 복구 권한으로 확장하지 않는다.
- `main`, 가장 최신 날짜, 많은 테스트 수만으로 정본 또는 정상 상태를 판정하지 않는다. 프로젝트 지침, 배포 기록, 소스 revision, 실제 데이터 원천을 대조한다.
- 브랜치의 설계·실험·검토안을 현재 운영 규칙으로 자동 승격하지 않는다. 서로 충돌하면 출처와 revision을 나란히 제시하고 해당 변경을 보류한다.
- 관련 SOP가 바뀌었으면 최신 정본을 다시 확인한다. 이 문서 끝의 고정 참조는 작성 근거이지 영구적으로 최신인 지침이 아니다.

### 역할

사고별로 조정 담당과 **리소스별 단일 쓰기 실행자**를 지정한다. 검토 담당은 대상 SOP가 요구하는 독립성을 지킨다. 같은 AI의 자기 검토를 다른 AI의 독립 검토로 보고하지 않는다. 실행자 연결 여부와 이번 작업을 실제로 수행했는지도 구분한다.

AIOps가 대상이면 기존 `docs/CONTROL_PLANE.md`를 따른다. 작성 시 확인한 정본은 라이브 변경에 Claude DESIGN/FINAL 검토, 사용자 직전 승인, Codex 실행 및 선언 리소스 lease를 요구한다. 이 제한을 다른 프로젝트에 무조건 이식하거나 비상이라는 이유로 생략하지 않는다.

## 3. 사고 유형별 절차

| 유형 | 먼저 확인 | 금지 | 복구와 검증 기준 |
|---|---|---|---|
| 데이터 오염·삭제 | 원천, 영향 레코드/셀, 변경 시각, 백업 시점, 그 이후 정상 입력 | 시트/테이블 통째로 재생성, 정상 입력을 덮는 전체 복원 | 제한된 위치에 현재 상태 보존 → 원천 대조 → 최소 patch를 모의 검증 → 승인 후 적용 → 영향 항목과 보존해야 할 정상 입력 재조회 |
| 코드·배포 오류 | 소스 SHA, 실제 배포 revision/ID, 환경, alias, 최근 정상 관측, 데이터·스키마 호환성 | 증거 없이 최신 브랜치 배포, 강제 push, 코드 롤백을 데이터 복구로 간주 | 격리된 복구 변경/이전 배포 후보 검증 → 필요한 배포 승인 → 실제 대상 revision과 핵심 동작 확인 |
| AI 동시 수정 | 실행자, 브랜치, worktree, 변경 경로, 작업 예약/lease, 원격 tip | 같은 브랜치 공동 쓰기, 자동 rebase/merge, 다른 AI 변경 삭제 | 각 변경을 안전한 위치에 보존 → 소유자/범위 확정 → 별도 작업 브랜치에서 통합 검증 → PR 검토. 다른 작업이 멈췄다는 응답 없이는 단일 실행자로 간주하지 않음 |
| 권한·토큰·외부 공개 | 노출된 리소스, 공개 경로/alias, 권한 범위, 관련 배포·감사 기록 | 토큰/키/원문을 채팅·GitHub에 붙이기, 파일 삭제만으로 노출 해소 선언 | 승인된 최소 차단 → 필요시 자격증명 폐기/교체와 사용처 갱신 → 허용된 범위의 익명 접근·잔여 alias·권한 재검증. 비밀번호를 추측하거나 인증을 우회하지 않음 |
| 정본·기억 혼란 | 지침별 출처와 revision, 최신 사용자 결정, 실제 배포/데이터 원천 | 새 저장소/새 기준을 임의 정본으로 만들기, 기억 문서로 프로젝트 사실 덮기 | 충돌표 작성 → 판정 가능한 실제 원천 확인 → 불명확한 결정만 사용자/책임자에게 올림 → 확정된 포인터만 갱신 |
| 연결 단절·실행 결과 불명 | 실행 ID, 요청 시각, 제공자 실행 상태, 대상의 현재 결과, 재시도 안전성 | 타임아웃을 미실행으로 단정, 같은 쓰기·청구·발송 무조건 재시도 | 읽기로 기존 요청 결과 대조 → 중복 여부 및 대상 SOP의 멱등성 확인 → 결과가 불명확하면 보류 유지. 새 실행은 별도 유효 승인이 있을 때만 수행 |

## 4. 상태와 증거 보존

기록할 최소 항목은 사고 ID, 관측 시각(시간대 포함), 프로젝트/환경, 소스와 대상 revision, 확인된 현상, 영향 범위, 미확인 항목, 마지막 정상 근거, 실제 수행한 조치다.

비밀키·토큰·고객/직원 원문·원본 데이터·백업은 GitHub에 넣지 않는다. private 저장소도 예외가 아니다. 접근 제한 저장소의 승인된 참조와 비식별 요약만 기록한다. 공유 전 URL의 토큰·서명 파라미터도 제거한다.

미커밋 변경에는 비밀정보가 섞일 수 있다. 먼저 안전한 위치에 보존하고 검토된 파일만 선별한다. 사고 현장에서 광범위한 staging, 작업 폴더 초기화, 삭제 명령을 실행하지 않는다.

AI Core에 접속할 수 없다면 이미 승인된 접근 제한 위치에 비식별 임시 기록을 남긴다. 본인 환경에 안전한 위치가 없으면 채팅에 비식별 요약만 남기고 원문을 복제하지 않는다. 연결 복구 후 정식 기록에 대조·인계한다.

## 5. 복구 실행 순서

1. **대상 고정:** 저장소·환경·리소스·현재 revision과 마지막 정상 근거를 기록한다. 현재 원격 상태와 실제 서비스가 서로 다른 경우 둘 다 남긴다.
2. **영향 확인:** 관련 쓰기 경로와 의존성만 조사한다. 데이터·스키마·외부 연동을 되돌려야 하는지 코드와 분리해서 판단한다.
3. **복구안 준비:** 최소 수정안, 보존할 정상 입력, 백업, 실패 시 중단/되돌림 방법, 검증 항목을 정한다. 비식별 자료로 별도 브랜치·격리 환경에서 검증한다.
4. **실행 직전 재확인:** 대상 revision, 범위, 허용 명령/변경, 실행자, 필수 검토, 승인 유효기간, lease를 확인한다. 원본·코드·범위가 바뀌었으면 기존 검증/승인의 유효성을 다시 판정하고 필요한 재검토를 받는다.
5. **승인 범위만 적용:** 실행 ID와 실제 결과를 기록한다. 다른 복구까지 묶어서 수행하지 않는다. 실패·예상 밖 결과·응답 불명은 추가 쓰기를 보류하고 재진단한다.
6. **실제 결과 검증:** 코드라면 실제 배포 revision과 핵심 경로, 데이터라면 원천 일치와 정상 입력 보존, 공개 사고라면 승인된 범위의 비인증 접근 결과를 확인한다. 증거는 같은 대상과 revision에 묶는다.
7. **재개 판정:** 아래 조건을 충족한 작업만 제한적으로 재개한다. 서비스가 복구되어도 원인 분석이나 재발 방지 작업은 별도로 미완료 상태를 남길 수 있다.

특정 프로젝트에서 검증하지 않은 복구 명령을 이 공통 문서의 만능 실행 명령으로 제공하지 않는다. 필요한 명령은 대상 SOP·현재 코드에서 확인하고, 복구안에 정확한 대상·예상 결과·되돌림 방법과 함께 넣는다.

## 6. 재개 조건 — 하나라도 없으면 해당 작업 보류

- [ ] 정본·프로젝트·환경·영향 범위와 현재 revision을 확인했다.
- [ ] 경쟁하는 쓰기가 없음을 확인했고, 실행자와 필요한 검토 담당이 정해졌다.
- [ ] 필요한 승인·리소스 범위·lease가 현재 실행에 유효하다.
- [ ] 필요한 현재 상태/백업 보존과 되돌림 방법을 확인했다. 적용 불가이면 이유와 대상 SOP의 대체 조치를 명시했다.
- [ ] 복구 대상의 필수 검증을 실제 실행했고, 미실행·실패·미확인 항목을 숨기지 않았다.
- [ ] 검증된 소스와 실제 반영 대상이 일치하고, 보호할 정상 데이터·기능이 유지된다.
- [ ] 중대한 미해결 문제 또는 계속되는 노출이 없고, 필요한 운영 재개 승인을 받았다.
- [ ] 재개할 작업, 중단 조건, 관측 담당·방법을 기록했다. 자동 감시가 없으면 없다고 명시했다.

체크리스트는 문서상 판정 보조다. 체크 표시나 상태 이름만으로 외부 실행을 승인하거나 복구 완료로 처리하지 않는다.

## 7. 사용자 보고와 작업 인계

설명은 다음 다섯 가지로 묶는다.

1. **확인된 문제와 영향:** 실제 관측과 의심을 구분한다.
2. **이미 한 일:** 읽기 진단, 요청한 중지, 실제 확인된 중지, 적용한 변경을 구분한다.
3. **아직 하지 않은 일:** 권한 부족·원본 불명·검증 실패 등 구체적 이유를 쓴다.
4. **필요한 결정:** 대상·행동·범위·위험·복구안을 제시하고 결정이 필요한 것만 요청한다.
5. **재개 여부와 남은 위험:** 근거가 없으면 완료가 아니라 미확인/보류로 보고한다.

인계에는 정확한 저장소/브랜치/commit SHA, 변경 파일, 실제 실행한 명령과 결과, 생략된 검사, 승인 참조, 남은 불확실성을 남긴다. 문서 생성, 검증 통과, 승인, 외부 실행, 실제 복구 결과를 하나의 완료 상태로 합치지 않는다.

사용자는 다음처럼 시작할 수 있다. 이는 자연어 요청 예시이며 자동 실행 명령이 아니다.

> AI코어 비상 점검. 해당 작업의 추가 쓰기를 보류하고 정본, 영향 범위, 마지막 정상 상태부터 확인해. 복구 변경은 필요한 승인을 확인한 뒤 진행해.

## 8. 종료와 재발 방지

복구가 확인되면 사고 현상, 확인된 원인/미확인 원인, 영향, 최소 수정, 검증 근거, 재발 방지책과 적용 범위를 기록한다. 원인 추정을 확정 사실로 저장하지 않는다.

공통으로 검증된 교훈만 AI Core에 비식별 요약/포인터로 남기고, 프로젝트별 상세와 원본은 해당 정본에 둔다. 다음 작업 시작 시 이번 실패 패턴을 확인할 수 있도록 진입 문서나 관련 SOP에 연결한다. SOP·권한 체계 변경은 별도 검토 대상이다.
